# bc250rd - read-only register reader for Windows (experiment E02)

| File | Purpose |
|---|---|
| `driver/bc250rd.c` | Software-only WDM driver. Does not bind to the GPU (the Basic Display driver keeps it), finds `1002:13FE` in PCI configuration space, maps BAR5 **read-only**, serves 32-bit reads for offsets in the allow-list. No write path to the GPU exists |
| `driver/allowlist.h`, `reglist.txt` | Generated by `gen_allowlist.py` from the Linux reference sweep (E03): 5542 named registers, 5398 offsets that were read on unit A before any driver without harm |
| `app/bc250rd_cli.c` | `info` and `sweep`: prints `<ip>.<name> <offset> <value>` exactly like the Linux sweep logs, name first, value after the read, so a hang names its register |
| `temp.py` | Run on the development PC: temperature of the target over SSH (`python temp.py [count [interval_s]]`), through `tools/win/target.py` |
| `apply-clock.ps1` | Runs on the target: the startup task's body, see "Clock and voltage" |
| `build.ps1` | Builds both without a WDK installation (WDK and SDK NuGet packages unpacked on a data disk) and test-signs the driver with a self-signed certificate |

Why an allow-list inside the driver: on this SoC a read of the wrong BAR5 address hangs the machine
(`docs/facts.md` M16). A generic "read physical memory" driver would also be a dangerous thing to publish;
this one can read 5355 fixed offsets of one PCI device and nothing else.

## On the target (elevated, test signing on)

```powershell
sc.exe create bc250rd type= kernel start= demand binPath= C:\BC250\bc250rd\bc250rd.sys
sc.exe start bc250rd
C:\BC250\bc250rd\bc250rd_cli.exe info
C:\BC250\bc250rd\bc250rd_cli.exe sweep C:\BC250\bc250rd\reglist.txt GC.    # run it through SSH, log on the other side
sc.exe stop bc250rd
```

## Temperature

`bc250rd_cli temp [count [interval_s]]` prints the SoC temperature (Tctl). Windows offers no ACPI thermal
zone on this board and amdgpu never reads the thermal block through MMIO, so there was no proven BAR5 path.
What is proven on this unit is the path of Linux' `k10temp`: SMN register `0x59800` (`THM_TCON_CUR_TMP`)
through the root complex's SMN index/data pair in configuration space (`00:00.0`, `0x60`/`0x64`). The driver
does exactly that, for an allow-list of one SMN address. It is the only write the driver issues, it goes to
the host bridge's index register (restored afterwards), never to the GPU. First reading under Windows, idle
desktop, Basic Display driver: 73 C (Linux after the fan was flipped: 72 C at the 1500 MHz idle level).

## Clock and voltage

`bc250rd_cli clock <MHz> <mV>` sends what amdgpu's overdrive interface sends on this APU: `RequestGfxclk`,
then `ForceGfxVid`, through the MP1 mailbox (`C2PMSG_66/_82/_90`). Limits are amdgpu's: 1000-2000 MHz,
700-1129 mV. `bc250rd_cli smu <hex> [param]` sends one allow-listed message (test, version, frequency and
vid queries, the two requests above, `UnforceGfxVid`). The setting is lost at reboot; on unit A a startup
task repeats `clock 1000 820`. This is the only write path to the GPU function, through its own one-page
mapping; everything else stays mapped read-only. Measured in E04 (`docs/facts.md` M22).

The startup task runs `apply-clock.ps1`, next to the CLI in `C:\BC250\bc250rd\`. At boot the task can start
before the driver service answers - seen after a bugcheck restart, where the task failed once and the GPU
stayed at the firmware default of 1500 MHz - so the script retries `clock` every 2 s for up to 3 minutes and
appends the outcome to `apply-clock.log` next to itself. Registering it (elevated, once per machine, already
done on unit A) is `powershell -ExecutionPolicy Bypass -File apply-clock.ps1 -Register`, which creates the
task "BC250 GPU clock 1000MHz 820mV" as SYSTEM at startup. `-MHz` and `-MilliVolt` change what is applied and
are carried into the registered task's command line.

## Limits

- Configuration space is read with `HalGetBusDataByOffset`, a legacy interface. Fine for a measurement
  tool that must stay out of the device stack, not for a product driver.
- Banked registers are read in whatever bank `GRBM_GFX_INDEX` currently selects; selecting a bank is a
  write and this tool does not write.
- Run on unit A: E02 run 001 (`evidence/windows/2026-09-21-E02-run-001/`). The temperature path was checked
  for plausibility against the Linux readings only, not against an independent sensor at the same moment.

### Verified clock requests

The CLI now reads GetGfxFrequency and GetGfxVid after clock and succeeds only
when replies match requested MHz and encoded VID. The clock-check command takes
MHz and mV arguments and performs only query messages. Exact VID comparison
reflects SMU encoding, not exact analogue voltage measurement. This uses bc250rd
SMU IOCTLs independently of miniport escapes. A historical successful task log
does not establish current clocks or ordering before GPU initialization.

## Typed clock client migration (M440)

Build the KMD CLI first, then pass its `bc250control.dll` to this build using
`-ControlDll` (the sibling import library is needed too). `clock` and
`clock-check` retain their command names but use the typed KMD transaction;
`smu` raw passthrough is removed. Temperature/PCI/register reads remain in the
reader. The new reader driver refuses legacy SMU writes. Deploy the DLL, clients
and reader together only after native KMD owner activation is ready; no fallback
to an old writer is allowed during PnP. Source migration is not lab deployment.
