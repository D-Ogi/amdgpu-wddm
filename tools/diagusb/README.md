# The BC-250 diagnostic USB stick

First contact with a BC-250. The stick boots Alpine Linux from RAM, reads a fixed list of GPU
registers **before any driver has touched the device**, then loads `amdgpu` and records what the
kernel makes of the same hardware. Nothing is installed, nothing on the machine is written to: the
whole system lives in RAM and is gone at the next power cycle.

The results are written to the stick and, so that a machine with no network and no second screen
is still readable, shown on the BC-250's own screen as QR codes. Scan them with a phone, paste the
text into `decode_qr.py` on the PC.

Nothing here has been run on a real BC-250 yet. Everything below was tested in QEMU, which has no
AMD GPU, so the probe path itself has only been exercised against a stand-in device (see
"Testing the MMIO path" below).

## What it measures

`bc250/diag.py`, phase by phase:

- **Phase A** - `amdgpu` is blacklisted on the kernel command line, so the GPU is still exactly as
  the BIOS left it. The probe maps BAR5 through `/sys/bus/pci/devices/*/resource5` and reads the
  registers listed in `bc250/probes.json` as single 32-bit accesses. It also reads the byte offsets
  the previous driver attempt used, to show what is really at those addresses.
- **Phase B** - `modprobe amdgpu`, then the kernel's view: `dmesg`, the IP discovery table, the
  firmware versions, and the same registers again, both raw and through amdgpu's own debugfs
  addressing. The two lists next to each other are the positive control for phase A.

Every offset in `probes.json` is generated by `tools/regcalc` from the AMD kernel headers
(`gen_probes.py`), never typed by hand, and the file carries an id that ties a result back to the
exact register list it was measured with.

## The two registers that are written

Phase A is read-only with two deliberate exceptions, both restored immediately afterwards:

| Register | Why |
| --- | --- |
| `GRBM_GFX_INDEX` | Selects which shader engine / shader array the per-bank registers are read from. Without it, `CC_GC_SHADER_ARRAY_CONFIG` and friends return whatever bank was last selected. Every driver, Linux included, writes this before such a read. Set back to broadcast (`0xE0000000`) in a `finally` block. |
| `SCRATCH_REG0` | A scratch register with no hardware meaning; `amdgpu` uses it for its own ring test. Two patterns are written and read back, which is the cheapest proof that the BAR is decoded and writable at all. The original value is restored. |

No other register is written, in any mode. `test_only_two_registers_are_ever_written` in
`test_diagusb.py` holds that line.

## Boot menu

| Entry | `bc250.mode` | What it does |
| --- | --- | --- |
| full | `full` | Phase A, then load `amdgpu` and run phase B. The default. |
| raw probe only | `noload` | Phase A only, `amdgpu` is never loaded. The two writes above still happen. |
| strictly read-only | `readonly` | Phase A with no MMIO writes at all, no `amdgpu`. |
| shell only | `off` | No diagnostics, just a root shell. Use it to look at results from an earlier run. |

## Build

Needs `7z` on PATH and network access (Alpine ISO, the `python3` package closure, the `segno`
wheel). Nothing needs admin rights.

```
python tools/diagusb/build_usb.py --work P:\BC-250\scratch --net P:\BC-250\secrets\net
```

`--net` is optional and points at a directory with `authorized_keys`, `wpa_supplicant.conf` and an
SSH host key. Those are secrets and are never part of this repo. Leave it out and the stick works
the same, without network access.

The result is a plain directory, `<work>/usbroot`. Unit tests:

```
python -m unittest discover -s tools/diagusb
python -m unittest discover -s tools/regcalc
```

## Test in QEMU

The tree boots as it stands, so the whole path (UEFI, overlay, package install, launcher,
diagnostics, QR display) can be checked before touching the real machine:

```powershell
$q = "$env:USERPROFILE\scoop\apps\qemu\current"
& "$q\qemu-system-x86_64.exe" -machine q35 -m 2048 -smp 2 -accel tcg `
  -drive if=pflash,format=raw,readonly=on,file=$q\share\edk2-x86_64-code.fd `
  -drive file=fat:P:\BC-250\scratch\usbroot,format=raw,if=none,id=stick,snapshot=on `
  -device qemu-xhci -device usb-storage,drive=stick,bootindex=0 `
  -vga std -display none -monitor tcp:127.0.0.1:45454,server,nowait `
  -serial file:P:\BC-250\scratch\qemu\serial.log
```

QEMU sees the host directory as it was when the VM started, so restart it after every rebuild.
Under TCG the boot takes about a minute and a half. The guest has no AMD GPU, so the run ends with
"no AMD GPU on the PCI bus" and a single QR code - that is the expected result there.

### Testing the MMIO path

Two environment variables point `Bar` at any BAR of any PCI function, which exercises the real code
path (sysfs `resource` file, `mmap`, 32-bit `ctypes` reads) instead of a stub. The device must have
**no driver bound**: once a driver has claimed a BAR, the sysfs `mmap` is refused with `EINVAL` on
a kernel built with strict devmem. That is exactly why `amdgpu` is blacklisted for phase A, and the
probe now says so when the mmap fails. In QEMU, add two devices that no in-tree driver binds to:

```
-device edu -device pci-testdev
```

```sh
# edu: 1234:11e8, BAR0 is 1 MiB, so every probe offset is inside it
BC250_TEST_DEV=/sys/bus/pci/devices/0000:00:04.0 BC250_TEST_BAR=0 python3 /media/usb/bc250/diag.py /tmp/r
# pci-testdev: BAR0 is 4 KiB, so every probe offset is outside it and reads back as None ('-')
BC250_TEST_DEV=/sys/bus/pci/devices/0000:00:05.0 BC250_TEST_BAR=0 python3 /media/usb/bc250/diag.py /tmp/r2
```

The positive control for the read path is the `edu` device's identification register, which reads
`0x010000ED` at offset 0:

```sh
python3 -c "import sys;sys.path.insert(0,'/media/usb/bc250');import diag;\
b=diag.Bar('/sys/bus/pci/devices/0000:00:04.0',0,readonly=True);\
print(b.size, hex(b.r32(0)), b.r32(b.size), b.r32(2))"
# 1048576 0x10000ed None None     <- in range, past the end, unaligned
```

Both variables must be set, the run is forced to `readonly`, the BAR is opened with writes refused
(`w32` raises), and the result is labelled `TEST_HOOK` in the verdict and carries `test` in the
summary, so such a run can never be mistaken for a measurement of a real GPU. The hook is never
used on the target.

## Write the stick

`write_usb.ps1` needs an elevated PowerShell 7. It erases the disk you name, so it checks first:
USB bus type, not the boot or system disk, at most 128 GB, the FriendlyName you pass in, and an
explicit switch. Find the number first, and check it again after every replug - disk numbers move:

```powershell
Get-Disk | Format-Table Number, FriendlyName, BusType, Size, IsBoot, IsSystem
```

Dry run (all guards, prints the plan, changes nothing):

```powershell
.\write_usb.ps1 -DiskNumber 8 -SourceDir P:\BC-250\scratch\usbroot `
  -ExpectedName 'Samsung Flash Drive FIT' -WhatIf
```

Then the real thing:

```powershell
.\write_usb.ps1 -DiskNumber 8 -SourceDir P:\BC-250\scratch\usbroot `
  -ExpectedName 'Samsung Flash Drive FIT' -IUnderstandThisErasesTheDisk
```

MBR, one active FAT32 partition of at most 32 GB labelled `BC250DIAG`, tree copied with robocopy,
then file count and total bytes compared against the source.

## On the BC-250

1. BIOS: boot mode **UEFI**, **Secure Boot off** (the stick is not signed). Put the USB stick first
   in the boot order, or use the firmware's boot menu.
2. Plug in a monitor and, if you have one, a keyboard. A keyboard is not required: the codes
   advance on their own every 20 seconds.
3. Boot the stick and pick a menu entry (the default runs after 5 seconds).
4. Wait. Phase A is quick, phase B can take a minute; `modprobe` is given 180 seconds before the
   probe gives up on it and writes what it has.
5. The screen shows the verdict lines on the left and one QR code at a time on the right. Any key:
   next code. `Q`: drop to a shell.
6. `poweroff` when done, or just cut the power - the stick is remounted read-only after the run.

Wi-Fi is optional and only enabled if the stick was built with `--net`. The ASUS USB-AC58 dongle
(USB ID `0b05:19aa`) is supported by the in-kernel `rtw88_8822bu` driver, so it works without any
extra firmware package. Wired Ethernet is configured by DHCP in any case. The `NET` line above the
verdict is live: it shows `no address yet` until DHCP succeeds, then `ssh root@<ip> (<interface>)`.

Measured so far, with the real dongle passed through to a QEMU guest: the driver binds, firmware
30.20.0 loads from the modloop, the scan finds the AP and authentication succeeds. Association,
the WPA handshake, DHCP and SSH have not been seen working yet (the emulated USB path is too slow
for the association to start), so treat Wi-Fi as a bonus and the QR codes as the primary channel.

## Reading the results

Three ways, in order of convenience:

- **The stick.** `bc250/results/run-NNN/`: `report.json` (everything), `summary.json` (what the QR
  codes carry), `dmesg.txt`, `qr-chunks.txt`, `launch.log`.
- **The QR codes.** Scan each one with any phone scanner and send the text. Order does not matter,
  duplicates do not matter, quoted mail or messenger junk around them does not matter:

  ```
  python tools/diagusb/decode_qr.py scan.txt
  ```

  It names any chunk that is missing, checks the CRC of the whole run, and prints the register
  values under their names - it refuses if `probes.json` is not the one the stick was built from,
  because the values travel positionally.
- **SSH**, if the stick was built with `--net`:

  ```
  ssh -i P:\BC-250\secrets\client\bc250diag_ed25519 root@<ip>
  ```

  The address is on the QR screen in the `NET` line, refreshed on every redraw (so a Wi-Fi
  association that completes minutes later still shows up). The results are under `/media/*/bc250`.

## Known limitations

- **Nothing has been tested on a real BC-250.** Every statement above about the hardware is an
  expectation, not a measurement.
- Phase A needs the GPU's BAR5 to be unclaimed. If something has bound to the device (the blacklist
  did not take, or a mode was booted that loads `amdgpu` first), the `mmap` fails with `EINVAL` and
  the run says so in `report.json`; phase B still runs. This was reproduced in QEMU against a BAR
  held by `bochs-drm`.
- Phase B depends on `amdgpu` loading. If it hangs the machine there is no way to report that from
  inside; this is why the QR codes are generated twice, once after phase A alone, and why
  `report.json` and `phaseB-started.txt` are flushed to the stick before the module is loaded. If
  the machine hangs, reboot into "shell only" and read `bc250/results/` from the stick.
- The QR codes are drawn straight into `/dev/fb0`, never through a graphics library. They are kept
  clear of the right-hand edge of the screen on purpose: the kernel's DRM fbdev emulation works out
  which part of the screen to refresh from the byte range of each write, and a write that ends
  exactly on a scanline boundary produces an empty rectangle, so the code lands in memory and is
  never displayed. Do not "tidy up" that margin.
- FAT32 on the stick is remounted read-write for the duration of the run. Pulling the power in the
  middle of it can leave the filesystem dirty; the results are flushed with `fsync` plus `sync`
  after every file, so at worst the last file is missing.
- QEMU proves the boot path, the launcher and the QR display, not the GPU probe.
