# M372 - AMD SDMA per-engine reset callback extracted, not runtime integrated

PROVENANCE: Linux amdgpu v6.18, commit7d0a66e4bb9081d75c82ec4957c50034cb0ea449, AMD MIT. Source callback and file hash in source.json.

Source review: amdgpu_sdma_reset_engine serializes an engine-reset mutex, stops scheduler admission unless handled by its caller, invokes stop_kernel_queue, the per-engine soft reset callback, and start_kernel_queue. The selected SDMA5 callback asserts the target SDMA bit in mmGRBM_SOFT_RESET, reads back, delays50us, clears that bit using the assertion readback, then reads back again. regcalc proves BAR5+0x08020. The generic IP soft_reset stub is a different path.

stop_queue brackets freeze/idle, halt and UTC_L1 disable with RLC safe-mode calls. The reset callback itself runs after that safe-mode exit. restore_queue enters a new scope, unfreezes and invokes gfx_resume_instance(restore=true): reprograms ring pointers from saved wptr, writeback/poll addresses, ring base, doorbells, UTC/cache policy, unhalts, enables RB/IB and runs a ring test. It does not free backing or reload firmware. Upstream reset_engine does not propagate the stop/start callback return values. Windows must require successful quiescence/restoration and must not import synthetic fence completion as proof of work.

New bc250_sdma_soft_reset_instance mechanically extracts the actual callback. Only function name/visibility, bounds check, omitted DRM debug print and shim delay differ; normalized body comparison passes. Return0 means the register sequence ran, not that reset took effect or stale DMA state was eliminated. No KMD caller. Existing quiesce_for_reload and installed117 are unchanged.

Required access order RWRDWR and exactly50us, two writes, preservation through release. Invalid instance/null do no access. Delay hook observes virtual time only. All pass.
