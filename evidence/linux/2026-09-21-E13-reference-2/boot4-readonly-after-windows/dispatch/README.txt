experiments/E13-linux-reference-2/dispatch_run.sh ran dispatch.py three times (raw amdgpu ioctls from python, libdrm
2.4.114's gfx10 memset shader and its 18-packet, 72-dword program, all constants generated by gen_dispatch.py):
  g1            1 workgroup, 1 KiB: 256 of 256 dwords hold 0x22222222
  g16           16 workgroups, 16 KiB (libdrm's own size): 4096 of 4096
  g16-memsync   the same with AMDGPU_IB_FLAG_EMIT_MEM_SYNC, so that the kernel prepends ACQUIRE_MEM: 4096 of 4096
Each: one submission, the wait returned at once with status 0, nothing in dmesg.

  g*.txt                   dispatch.py's output: every ioctl, the IB dwords annotated, the destination before and after
  g*-events.txt            amdgpu's trace events around the run. The DRM scheduler put all three on comp_1.1.0 (not on
                           compute ring 0); each submission raised two client 20 / source 181 vectors with ring id 5,
                           one per fence (the VM flush's and the job's)
  after-ring-comp_1.1.0.txt  that ring afterwards (od -t x4; the first three words are rptr, wptr, driver wptr): what
                           amdgpu wraps around a user IB on a compute ring: ACQUIRE_MEM (third run only), pipeline
                           sync, VM flush, fence, INDIRECT_BUFFER with VMID 2, fence, NOP padding to 256 dwords
  after-ring-comp_1.0.0.txt, after-ring-sdma1.txt   the neighbours, for completeness (sdma1 carried the page table updates)
The first run of the script dumped comp_1.0.0 after each dispatch, the wrong ring; those three dumps were dropped on the
