## Rules

- **translated**: the dispatch table of `emit_dxil_instruction` has a handler for the opcode.
- **translated-partial**: the handler has an error path for a valid D3D12 input. A helper that the handler calls counts too, to two levels. The note gives the file:line of each path. These error paths do not count:
  - Input attachments. They are an engine-internal binding, and a D3D12 shader cannot name one.
  - The internal consistency checks of the ray query analysis pass.
  - The checks of the engine's own options.
  - The DXBC input path.
  - The AMD AGS and NVAPI extension paths. They are not DXIL semantics.
- **refused**: the handler returns false on every path.
- **missing**: the opcode has no handler. An opcode at or above `DXIL::Op::Count` (335) stops at `opcodes/opcodes_dxil_builtins.cpp:469`. An opcode without a handler stops at `opcodes/opcodes_dxil_builtins.cpp:477`.
- dxil-spirv puts its internal opcodes (`Extended*`) after its last DXIL opcode, from 312. DXC now uses these numbers for shader model 6.10. Such an opcode is **missing**. The note names the internal handler that it runs.
- The SM column is the hctdb value. Some operations have only vector overloads. Such an operation exists only on a native vector, and DXIL has native vectors from shader model 6.9. The SM* column gives 6.9 for these operations. The totals and the reach column use SM*.
- **Reach** is for the installed route: the D3D12 shell and the engine behind it. `yes`: the reported shader model and the reported caps admit the operation. `no`: they do not admit it. `cond`: the cap is an engine answer, and the evidence here does not give its value.

A static matrix finds a missing case. It cannot find a wrong translation. The candidate list names the operations that have a case but doubtful semantics. Use it to select runtime tests.

## Candidates for runtime tests

These operations have a case, or their opcode reaches a handler, but their semantics look doubtful.

| Operation | Where | Why |
|---|---|---|
| `opcodes 312-334` | `dxil.hpp (DXIL::Op::Extended*), opcodes/opcodes_dxil_builtins.cpp` | These are 23 SM 6.10 operations. emit_dxil_instruction and both analysis passes read each one as the internal opcode of the same number. They run that handler and do not refuse the operation. Today the shader model ceiling stops these programs. Before SM 6.10 work, move the internal opcodes. |
| `BarrierByMemoryType` | `opcodes/dxil/dxil_workgraph.cpp:418` | Under the Vulkan memory model, DEVICE_SCOPE gives a workgroup memory scope. The REORDER_SCOPE bit (0x8, DXC DxilConstants.h) is not in the barrier semantics of dxil.hpp, so emit_barrier ignores it. Test cross-group UAV visibility and SER reorder barriers. |
| `BarrierByMemoryHandle` | `opcodes/dxil/dxil_workgraph.cpp:461` | The handler returns false when the handle does not come directly from AnnotateHandle. An example is a select or a phi of two handles. With GROUP_SCOPE, the analysis pass refuses the same case (opcodes/opcodes_dxil_builtins.cpp, case BarrierByMemoryHandle). |
| `BarrierByMemoryHandle` | `opcodes/dxil/dxil_workgraph.cpp:402` | It uses emit_barrier, as BarrierByMemoryType does. The scope and REORDER_SCOPE questions are the same. |
| `AllocateRayQuery2` | `opcodes/opcodes_dxil_builtins.cpp:1547` | The TraceRayInline analysis looks only for AllocateRayQuery. Thus every SM 6.9 ray query object counts as indirectly indexed (uses_non_direct_indexing). That path is slower. Test that the results are equal. |
| `AllocateNodeOutputRecords`, `FinishedCrossGroupSharing` | `opcodes/opcodes_dxil_builtins.cpp` | These operations return a value and have side effects (hctdb). `dxil_instruction_has_side_effects` does not list them. Thus the dead-code option removes them when the value has no use. The option is off by default (`opcodes/converter_impl.hpp:793`). vkd3d-proton does not set it, so the risk is latent on our route. |
