# Pending release-notes lines: the DirectFlip handshake, driver half (KMD 0.7.209.1)

This file is not a release. It holds the tester-facing lines for the next tester release notes. The release
step copies the lines into `docs/testing/release-notes/<version>-tester.N.md` and deletes this file.

## Known behaviour

- This version carries the driver half of a change that lets a game put its own picture on the screen without
  the desktop copying it first. Nothing about it is on by default, and no part of the picture path changes in
  this version: a start of this driver behaves exactly as 0.7.208.1 did. The other half, in the user-mode
  drivers, is not in this release.

- The support report holds three more lines about what the driver saw: which kind of description each surface
  arrived with, what the system asked for on each change of the displayed picture, and how many pictures the
  system sent through the desktop. These are counts only. They make a report about a black screen or a frozen
  picture answerable without a second run.

## For the lab operator, not for testers

- New setting `EnableDirectFlipHandshake` (REG_DWORD, under the driver service's `Parameters`, default 0). At
  1 the driver tells the desktop's user-mode driver that it will accept a game's own picture buffer. The
  driver ANDs the setting with every other setting the picture path needs (`EnableScanoutAdmit`,
  `EnableMmio`, `EnableDcnWrite`, `EnableVidPnFlip`) and with the state of the hardware it found at the
  start, so this setting alone can never make the desktop stop copying a picture the driver would then
  refuse to display. The start log says which input closed it.

- Rollback: set the value to 0 and restart the adapter. The driver then writes nothing in the new part of its
  reply, at any size, and is byte for byte 0.7.208.1 for every reader. `driver/kmd/README.md` has the order
  of the wider switches.
