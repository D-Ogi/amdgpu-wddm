# Pending release-notes lines: the driver's own timeout on long GPU work (KMD 0.7.216.27)

This file is not a release. It holds the tester-facing lines for the next tester release notes. The release
step copies the lines into `docs/testing/release-notes/<version>-tester.N.md` and deletes this file.

## Fixed

- **A long piece of GPU work could stop Windows with a blue screen, even when the work was healthy.** The driver
  kept a timer of its own and gave every piece of work on the graphics engine half a second to finish. Half a
  second is enough for a frame of a game. It is not enough for one step of a large language model, which can take
  half a second or more on purpose. When that timer ran out the driver closed the engine, and from there the
  machine always went down the same way: a blue screen with the code `VIDEO_TDR_FAILURE` (0x116). The work
  itself had finished correctly in both of the crashes we captured.

  The driver now takes its budget from the Windows setting that already governs this, `TdrDelay`, and adds two
  seconds, so Windows always acts first. On a machine where our control application set the recommended
  `TdrDelay` of 10 seconds, the driver's own budget is 12 seconds. The driver also watches the graphics engine
  while the work runs and gives it the full budget again whenever it sees it move forward, so a job that takes
  minutes and keeps working is never stopped at all. Nothing in the driver waits longer for a job that is really
  stuck: Windows' own recovery reaches it first, and that recovery works.

  You can set the budget yourself if you have a reason to. Add a `SubmitWatchdogMs` value (a DWORD, in
  milliseconds) under the driver's `Parameters` key. The driver never accepts a value below `TdrDelay`, because
  that is the setting that caused this, and it says in its log which value it used:
  `wddm: submit watchdog 12000 ms (TdrDelay 10000 ms, setting 0, default)`.

- **A support report can now say how long a piece of GPU work actually took.** The timeout line used to print
  the budget, so it said "after 500 ms" whether the work had taken half a second or five. It now prints three
  measured times - how long the work was running, how long it waited for its turn, and how long the engine
  showed no progress - and the summary at the end of a run carries the longest of each. If a workload is close
  to the budget on your machine, the log says so without a crash.

- **A driver timeout no longer has to end in a blue screen.** When Windows asks the driver to recover an engine
  and the accused work has quietly finished in the meantime, the driver used to answer "cannot do that", and
  Windows then had no way out but the blue screen. It now tells Windows which piece of work to treat as
  cancelled, which is what the Windows contract asks for in that exact situation, and reopens the engine. The
  program that owned the work loses its graphics device and reports an error. The machine stays up.

## Known behaviour

- A program whose GPU work really is stuck now freezes for the length of `TdrDelay` (10 seconds with our
  recommended setting) instead of half a second, before Windows recovers it. That is the Windows budget, and the
  trade is deliberate: the half-second version ended in a blue screen.
- One place still keeps the old half-second bound on purpose. A new piece of work that cannot start because
  another program's work is still on the engine waits at most half a second for its turn, because that wait holds
  a Windows thread. In practice that wait is measured in microseconds.
- The driver writes four more log lines per run than 0.7.216.26 (one at start-up, two at a timeout, two in the
  summary). The log keeps the same number of lines in total, so a long run wraps a little earlier.
