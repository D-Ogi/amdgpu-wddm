# Pending release notes: private submit watchdog (KMD 0.7.216.27)

This is an implementation candidate, not a released or lab-validated fix. Copy validated results into the
next tester release notes before deleting this file.

## Changes

- The private graphics-submit watchdog no longer uses a fixed 500 ms budget. Absent `SubmitWatchdogMs`, its
  budget is `TdrDelay` plus 2 s: 12 s when `TdrDelay` is 10. An explicit REG_DWORD value in the driver's
  `Parameters` key is clamped to five minutes and then raised to the `TdrDelay` duration if necessary.
  Windows starts its timeout at its preemption request, while the private timer tracks head admission and
  observed activity. The margin does not guarantee which timeout fires first.
- Activity changes can restart the private observation window. Activity, priming, observation-gap resets and
  timer re-arms have separate counters. Fetch-register activity is not proof that a packet is completing.
- Timeout diagnostics report software-head age, queue wait and observed token staleness. The summary's head
  high water is a sampled software-head age. It can miss the last interval before retirement and is not GPU
  execution duration.
- An empty-ring recovery may name the completed fence as aborted only when the per-node completion and
  publication state is authoritative. The guarded recover/refuse cases are specified in
  `docs/design/hang-recovery.md`. A successful recovery still loses the affected application's device.

## Limits and validation

An alternating activity token can keep restarting the private window without completion. A healthy long shader
can conversely leave the token unchanged. Windows owns TDR, but a genuine hang or uncertain completion state can
still end in 0x116. No general GPU reset is established by this change.

The CPU submit-hold wait remains 500 ms. Exhausting the completion queue can still refuse a submission. The
longer GPU watchdog budget does not remove that path. A refusal is not a guaranteed recoverable device loss.

Host controls establish decision logic, not hardware recovery. The dense gemma-4-12b QAT q4_0 acceptance workload
must complete `-ub 512 -p 512 -n 128 -r 3` on the candidate, with successful cleanup and no timeout or recovery.
If it does not fit the current 8192 MiB UMA configuration, a named fitting dense workload is a partial control,
not acceptance of the original case. Lab validation remains pending.
