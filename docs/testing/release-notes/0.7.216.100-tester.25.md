# amdgpu-wddm 0.7.216.100-tester.25

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and amdgpu-wddm Control of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes a record that
only this installer and this control program read.

The release before this one is 0.7.216.100-tester.24. This release replaces it. The notes of 0.7.216.100-tester.24
list the changes since 0.7.216.100-tester.23, and they apply to this release too, with the changes below.

## New

- **The fan goes to full speed while the machine works hard.** Until now the fan followed the temperature: it sped
  up after the board had already become hot. The driver can see the work itself, so it no longer waits. Work counts
  as heavy while the GPU is busy above its idle clock, or the chip draws more than 85 watts (processor and graphics
  together), or the temperature climbs by more than three degrees in three seconds. When any one of those holds for
  about two seconds, the fan goes straight to full speed. It stays there for half a minute after the
  work stops, and then slows down the gentle way it always did. A single busy second, a menu or a short compile,
  does not start it. The fan is never made quieter by this: where the temperature asks for more, the temperature
  wins.
- **A switch for it in amdgpu-wddm Control**, in the Case fan card of the Performance page: "Full fan speed under
  heavy load". It is on after the installation. Turn it off if you would rather have a quiet machine than a cool
  one, and the driver then follows the temperature alone. The switch takes effect at the next restart of Windows,
  and the card says so and offers the restart. The switch works with every fan choice in that card, the board's
  own setting included.
- The kernel-mode driver is version 0.7.216.26.

## Fixed

- **A game could stop drawing and never start again.** Each graphics device has one alarm clock that the driver
  uses for short waits. Two pictures of one game, on two queues or two windows, could both wait for that one
  alarm. The alarm wakes one of them, and the other waited for ever: the game was alive, used no processor and
  drew nothing. Both of these waits are now short, and the driver decides what to do next by looking at the work
  itself, so a missed alarm costs a millisecond instead of the rest of the game. This affects the frame rate
  limiter of the graphics settings and the Direct3D 12 frame latency wait.
- **Video recording with the BC-250 encoder keeps the right picture.** The encoder smooths the edges between the
  blocks of a picture, and the fast way of doing it needed every part of the work to run at the same time, which
  Direct3D does not promise. When it did not, the encoder smoothed the blocks in the wrong order, said nothing,
  and the picture drifted further off in every frame that followed. The safe order is the default again. The fast
  one is still there for measurements, as `BC250_MFT_DEBLOCK=rows`.
- **The encoder answers for the lock on your program's graphics device.** It asked the Media Foundation device
  manager for the lock and then went on with the work whether it got it or not, so its own work and your
  program's own drawing could reach one device at the same time. It now stops with an error instead, and takes
  the lock back correctly when it is done.
- **The driver no longer promises an instant change of the picture format.** When a program asks whether it may
  put its own picture on the screen and change the colour format in the same breath, with no wait for the
  screen's own refresh, the answer is now no. The hardware of this chip changes that format only at the refresh.
  Nobody reported a wrong picture from it. This is the answer the rule asks for, and the right answer keeps the
  path honest. Programs that keep one format, which is all of them we test, are not affected.
- **An installation or an uninstallation can no longer hang for ever on the sound device.** Both restart the
  sound part of the adapter. That restart had no time limit, so a stuck restart held the whole install. It
  now has one, and the installer tells you when the limit is reached and that it stopped nothing.
- **The fan hand-back no longer runs in a time-critical part of the driver.** When the fan watchdog gives the fan
  back to the board, the handshake with the board's own chip can take milliseconds. That work now runs in a
  normal part of the driver where a wait is allowed. The fan behaves as before. What changes is that the
  hand-back can no longer hold up the rest of the system while it runs.
- **The processor's top speed is read properly.** The driver measures the highest clock the processor reaches
  under load once per start, and it used to stop at the first reading it liked. It now finishes its measurement
  and keeps the highest reading. That number is what the driver puts back when it restores the processor, so it
  was too low before on some starts.

## Known issues

- **A large dense language model can stop Windows with stop code 0x116.** On the lab machine two dense models
  (about 12 and 27 billion parameters) stopped Windows on their first big piece of work, both times at
  llama.cpp's default batch of 512 tokens. The mixture-of-experts models finish at 512. The cause is in our
  driver: it has its own limit of 500 ms for one piece of GPU work, much shorter than the 10 seconds that Windows
  allows. A long but healthy piece of compute work passes that limit, and the recovery that follows fails. Until
  the fix ships, use `-ub 128` for a dense model. On the lab machine it finished every run, also with three
  repeats and with a 4096-token context, and it was faster than `-ub 256`. `-ub 256` finished once, with no
  repeated run, so we do not recommend it yet (issue BD-114). After such a stop the driver's automatic clock
  control is left switched off, so check the Tuner page of amdgpu-wddm Control.
- The fan's work under load has not run on a machine yet. The behaviour above is tested in the driver's own
  tests, not on hardware, and this release is the first one a tester can measure it with. If your fan is loud
  when it should be quiet, or quiet when the machine is hot, tell us, and say what the Case fan card shows.
- A program that the router sends to the processor path gets Direct3D feature level 10_0 only. With the release
  setting gpu-default this affects programs whose image the router cannot resolve. Keep the router at gpu-default
  (issue #24).
- Without administrator rights, `bc250kmd_cli clock read` gives no clock and no temperature. Use
  `bc250kmd_cli dpm` in its place (issue #7).
- The desktop compositor composes a full-screen game again while another window covers part of it, for example a
  notification. The driver has no overlay path for such a window yet.
- A screenshot or a screen recording of a full-screen Direct3D 12 game can be black. The game puts its own
  picture on the screen, and the compositor does not get the frames. To record such a game, set
  `AMDGPU_WDDM_D3D12_EXPERIMENT=scanout-flip-off` for it.
- The catalog file of the kernel driver (`bc250kmd.cat`) is still different in every build, because every build
  signs a new one. The driver image is the same in every build.
- The known issues of 0.7.216.100-tester.24 apply.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.
- The fan's full speed under heavy load is `FanLoadBoost` (`REG_DWORD`) under the `Parameters` key of the driver.
  The driver reads it when it starts, so a change needs a restart of Windows. On is the default and leaves the
  value absent. The switch in amdgpu-wddm Control writes 0 when you turn it off. Use the switch rather than the
  registry: the page knows when a restart is needed.
- The safe order of the encoder's block filter is the default and needs no setting. `BC250_MFT_DEBLOCK=rows` in
  the environment of a program asks for the fast order, which can give a wrong picture, and is for measurements
  only.
- `EnableDpAudioContainerId`, `EnableRingVmFlush`, `TdrDelay` and the shader cache of the 64-bit Vulkan driver
  stay as 0.7.216.100-tester.24 set them. `TdrDelay` is 10 seconds, written by the installation, and the
  uninstaller puts your earlier value back.
- The graphics settings are `REG_DWORD` values under `HKLM\SOFTWARE\amdgpu-wddm\Graphics` for all games and under
  `HKLM\SOFTWARE\amdgpu-wddm\Graphics\Applications\<program file name>` for one game. No value is set after the
  installation, so each game keeps its own settings until you change one.
- The AMD-format driver version on the Graphics page stays off after the installation, and no installation of
  this package writes it. Windows asks a driver not to change that number after it is installed, and changing it
  can stop Windows Update from working properly on the adapter. Turn it on only for a game that refuses to
  start with the real number, and turn it off again afterwards.

## If something goes wrong

- If the fan is too loud, turn off "Full fan speed under heavy load" in the Case fan card of the Performance
  page and restart Windows. Then tell us what the machine was doing.
- If a recording made with the BC-250 encoder looks wrong, send us the recording and say whether
  `BC250_MFT_DEBLOCK` was set for the recording program.
- If the sound device of your monitor disappears or stops after this release, set `EnableDpAudioContainerId` to 0
  and restart Windows. Then tell us what happened.
- If a Vulkan game starts badly or draws wrongly, delete `%LOCALAPPDATA%\mesa_shader_cache` and start it again. If
  that helps, set `MESA_SHADER_CACHE_DISABLE=true` for the game and tell us.
- If Quake II RTX or another ray tracing program loses its graphics device, send us the support report with the
  name of the program and the mode you ran.
- If a game has a black screen or a wrong picture in full screen, set
  `AMDGPU_WDDM_D3D12_EXPERIMENT=scanout-flip-off` for that game and start it again. Then tell us what happened.
- If a game fails after you change a graphics setting, set the setting back to "Application decides" on the page
  where you changed it.
- If Windows stops with stop code 0x116 after a GPU job stops, send us the support report. It holds the driver
  log and the result of each recovery.
- Send us the support report from amdgpu-wddm Control. It holds the driver log and the stored graphics settings.
