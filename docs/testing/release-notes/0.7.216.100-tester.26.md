# amdgpu-wddm 0.7.216.100-tester.26

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and amdgpu-wddm Control of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes a record that
only this installer and this control program read.

The release before this one is 0.7.216.100-tester.25. This release replaces it. The notes of 0.7.216.100-tester.25
list the changes since 0.7.216.100-tester.24, and they apply to this release too, with the changes below.

## New

- **The driver's own limit for one piece of GPU work now follows the Windows timeout.** Windows gives a piece of
  GPU work 10 seconds in this release. The driver had a second, private limit of its own of half a second, which
  was much shorter, and a long piece of honest work ran into it. That limit is now the Windows timeout plus two
  seconds, 12 seconds as this release installs it, and the driver starts it again whenever the work makes
  progress. You can set it yourself with `SubmitWatchdogMs`, below.
- The kernel-mode driver is version 0.7.216.27.
- The 64-bit Vulkan driver is a new build, with the three Vulkan fixes below.

## Fixed

- **A large language model no longer stops Windows with stop code 0x116** (issue #36). Dense models stopped
  Windows on their first big piece of work at llama.cpp's own default batch of 512 tokens, and the notes of
  0.7.216.100-tester.25 asked you to use `-ub 128` instead. The cause was the driver's private half-second limit
  above: the work was healthy, it simply took longer than half a second, and the recovery that followed failed.
  On the lab machine the model that stopped Windows twice that morning (a 12-billion-parameter dense model,
  `-ub 512 -p 512 -n 128`, three repeats) now runs to the end: 207 tokens a second reading the prompt, 33 tokens
  a second writing, no timeout, no recovery and no stop. You no longer need `-ub 128` for that model. Please tell
  us what your own models do.
- **A long wait in a Vulkan program no longer ends with a lost graphics device after ten seconds.** The 64-bit
  Vulkan driver waited for the GPU in one piece of ten seconds, and a piece of work that honestly took longer
  was reported to the program as a lost device. It now waits in one-second steps for up to two minutes, and it
  checks the graphics device between the steps, so a device that has really gone away ends the wait at the next
  step instead of holding the program for the whole two minutes.
- **The Vulkan driver keeps the right answer while it makes memory resident.** When it put memory in place for
  the GPU it used an answer that Windows does not promise for that call, and it could then go on while an
  earlier piece of work was not finished. It now keeps the newest answer it was promised and waits for that
  one. Nobody reported a wrong picture from this.
- **A monitor whose description the driver cannot read is written in the log again.** One answer of the driver,
  which is the designed answer of the sound part of a DisplayPort monitor, was taken as "not worth logging"
  everywhere in the driver instead of in that one place. A monitor that serves no description gives the same
  answer for a real fault, and such a monitor appeared in the log 6 times instead of 64. Log lines only: no
  behaviour changes, and nothing you can see on the screen.

## Known issues

- **The fix above is measured on one dense model.** The lab machine ran a 12-billion-parameter dense model at
  the default batch to the end, three repeats. The 27-billion-parameter model that also stopped Windows has not
  been run again on this release, and the driver's longer limit does not promise that every long piece of work
  ends well: Windows still owns its own 10-second timeout, and a real hang still ends in stop code 0x116. If a
  model stops Windows on your machine, send us the support report and the exact llama.cpp command (issue #36).
- After a stop with code 0x116 the driver's automatic clock control is left switched off. Check the Tuner page
  of amdgpu-wddm Control after such a stop.
- **The three Vulkan fixes above are in the 64-bit Vulkan driver only.** The 32-bit Vulkan driver of this
  release is the same build as in 0.7.216.100-tester.25, so a 32-bit Vulkan program still reports a lost
  graphics device after ten seconds of one wait. We know of no 32-bit Vulkan program that waits that long.
- The two-minute wait of the Vulkan driver is a chosen bound, not a measured one. No program of ours needed
  more than a second. If a Vulkan program seems to hang for about two minutes and then reports a lost device,
  that is this bound, and we want to hear about it.
- The fan's work under load is measured on one load, on one machine. On the lab machine, under a path tracer
  that held the graphics at full clock for 165 seconds, the fan was at full speed within 15 seconds of the
  start with the default of 0.7.216.100-tester.25, and after 102 seconds with the switch off: about a minute
  and a half earlier. Your case and your fan are not ours, and a language model, a compile or a game is not a
  path tracer. If your fan is loud when it should be quiet, or quiet when the machine is hot, tell us, and say
  what the Case fan card shows.
- A program that the router sends to the processor path gets Direct3D feature level 10_0 only. With the release
  setting gpu-default this affects programs whose image the router cannot resolve. Keep the router at gpu-default
  (issue #24).
- Without administrator rights, `bc250kmd_cli clock read` gives no clock and no temperature. Use
  `bc250kmd_cli dpm` in its place (issue #7).
- The desktop compositor composes a full-screen game again while another window covers part of it, for example a
  notification. The driver has no overlay path for such a window yet.
- A screenshot or a screen recording of a full-screen Direct3D 12 game can be black. The game puts its own
  picture on the screen, and the compositor does not get the frames. To record such a game, set
  `AMDGPU_WDDM_D3D12_EXPERIMENT=scanout-flip-off` for it.
- The 64-bit Vulkan driver of this release is a new build, so the shader cache it wrote for an earlier release
  is not read any more. The first start of a Vulkan game takes longer than it did, once.
- The catalog file of the kernel driver (`bc250kmd.cat`) is still different in every build, because every build
  signs a new one. The driver image is the same in every build.
- The known issues of 0.7.216.100-tester.25 apply, except the stop with code 0x116 at the default batch, which
  is the first item of Fixed above.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.
- The driver's private limit for one piece of GPU work is `SubmitWatchdogMs` (`REG_DWORD`, milliseconds) under
  the `Parameters` key of the driver. Leave it absent, which is the default, and the driver uses `TdrDelay`
  plus two seconds. A value you write is held to five minutes at the most and is never shorter than `TdrDelay`.
  The driver reads it when it starts, so a change needs a restart of Windows.
- The fan's full speed under heavy load is `FanLoadBoost` (`REG_DWORD`) under the `Parameters` key of the driver.
  The driver reads it when it starts, so a change needs a restart of Windows. On is the default and leaves the
  value absent. The switch in amdgpu-wddm Control writes 0 when you turn it off. Use the switch rather than the
  registry: the page knows when a restart is needed.
- The safe order of the encoder's block filter is the default and needs no setting. `BC250_MFT_DEBLOCK=rows` in
  the environment of a program asks for the fast order, which can give a wrong picture, and is for measurements
  only.
- `EnableDpAudioContainerId`, `EnableRingVmFlush`, `TdrDelay` and the shader cache of the 64-bit Vulkan driver
  stay as 0.7.216.100-tester.25 set them. `TdrDelay` is 10 seconds, written by the installation, and the
  uninstaller puts your earlier value back.
- The graphics settings are `REG_DWORD` values under `HKLM\SOFTWARE\amdgpu-wddm\Graphics` for all games and under
  `HKLM\SOFTWARE\amdgpu-wddm\Graphics\Applications\<program file name>` for one game. No value is set after the
  installation, so each game keeps its own settings until you change one.
- The AMD-format driver version on the Graphics page stays off after the installation, and no installation of
  this package writes it. Windows asks a driver not to change that number after it is installed, and changing it
  can stop Windows Update from working properly on the adapter. Turn it on only for a game that refuses to
  start with the real number, and turn it off again afterwards.

## If something goes wrong

- If Windows stops with stop code 0x116 while a language model or another long GPU job runs, send us the support
  report with the exact command you ran, the model and its batch size. Then check the Tuner page of amdgpu-wddm
  Control, because the automatic clock control is left switched off after such a stop.
- If a Vulkan program hangs for about two minutes and then says that the graphics device was lost, send us the
  support report and say what the program was doing.
- If the fan is too loud, turn off "Full fan speed under heavy load" in the Case fan card of the Performance
  page and restart Windows. Then tell us what the machine was doing.
- If a recording made with the BC-250 encoder looks wrong, send us the recording and say whether
  `BC250_MFT_DEBLOCK` was set for the recording program.
- If the sound device of your monitor disappears or stops after this release, set `EnableDpAudioContainerId` to 0
  and restart Windows. Then tell us what happened.
- If a Vulkan game starts badly or draws wrongly, delete `%LOCALAPPDATA%\mesa_shader_cache` and start it again. If
  that helps, set `MESA_SHADER_CACHE_DISABLE=true` for the game and tell us.
- If Quake II RTX or another ray tracing program loses its graphics device, send us the support report with the
  name of the program and the mode you ran.
- If a game has a black screen or a wrong picture in full screen, set
  `AMDGPU_WDDM_D3D12_EXPERIMENT=scanout-flip-off` for that game and start it again. Then tell us what happened.
- If a game fails after you change a graphics setting, set the setting back to "Application decides" on the page
  where you changed it.
- Send us the support report from amdgpu-wddm Control. It holds the driver log and the stored graphics settings.
