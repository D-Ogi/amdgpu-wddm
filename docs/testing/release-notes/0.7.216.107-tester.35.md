# Nagi (amdgpu-wddm) 0.7.216.107-tester.35

A tester release of Nagi (amdgpu-wddm), an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It
replaces 0.7.216.106-tester.34.

It is signed with our **test certificate** and still requires Windows test-signing mode.

## How to install

Copy `amdgpu-wddm-setup-0.7.216.107-tester.35.exe` to a local folder and double-click it. Or unpack the zip file
and double-click `setup.exe` in the folder it makes. You can install this release over tester.31, tester.31v2,
tester.31v3, tester.32, tester.33 or tester.34: you do not have to uninstall first. The setup updates the installed
release and keeps the settings that you changed. Before an update from tester.31 or tester.31v2 on Windows 11 24H2 or
later, read the first known issue. Windows reports the driver package version as 40.7.216.107, which is higher than
the version of each of these releases.

## New

- **Large VRAM pages.** The driver now maps the graphics memory in pages of 2 MiB where it can, in place of 4 KiB.
  The graphics chip then needs fewer page table reads. llama.cpp on HIP gains the most: Qwen3-8B Q8_0 processes a
  prompt about 2.3 times as fast (pp512 252 -> 572 tokens a second). The cost is the graphics memory below the first
  1 GiB boundary of the carve-out, about 220 MiB on our BC-250. It is on by default. To turn it off, open a command
  prompt as administrator, run `bc250kmd_cli state set LargePages 0` and restart the computer.
- **llama.cpp on HIP is now as fast as ROCm on Linux, or faster.** The llama.cpp that the setup offers is a new
  build with the BC-250 patches of the bc250-rocm project (Artur Andrzejczak, github.com/akandr/bc250-rocm), which we
  ported to our HIP runtime. Measured on our BC-250 at 1500 MHz with 40 graphics cores and the 12 GiB carve-out, with
  this release installed, against the published ROCm figures of bc250-rocm on Linux (llama-bench, Flash Attention on,
  pp512 and tg64 in tokens a second, the mean of two runs):

  | Model | pp512 Nagi | pp512 ROCm | tg64 Nagi | tg64 ROCm |
  |---|---:|---:|---:|---:|
  | qwen2.5-1.5B Q4_K_M | 2158.0 | 1798.6 | 198.1 | 196.7 |
  | Qwen3-8B Q8_0 | 577.7 | 409.4 | 39.9 | 38.5 |
  | Qwen3.6-35B-A3B UD-IQ2_M | 662.8 | 588.8 | 74.6 | 71.2 |

  The 8B and 35B models need the 12 GiB carve-out to fit in the graphics memory. Perplexity and the llama.cpp
  backend tests give the same results as before.
- **A model larger than the graphics memory now loads.** The part that does not fit goes to system memory, which is
  slower. Before, such a model stopped the HIP device when it loaded. For example, Qwen3-8B Q8_0 (8.1 GiB) now runs at
  the default 8 GiB carve-out.
- **Faster HIP waits.** A HIP program that waits for the graphics chip now reads the result first for a short time,
  before it asks Windows to wait. In llama.cpp this gives about 5 % more tokens a second when it generates text
  (qwen2.5-1.5B tg64 189 -> 198).
- **Direct3D 12: application-specific driver state.** A Direct3D 12 capture and replay tool can now get the driver
  settings of the captured game and give them back to the driver in the replay.

## Fixed

- **Counter-Strike 2 (Direct3D 11) no longer stutters for minutes after the start of a map.** The Direct3D 11 driver
  compiled each new pipeline on the render thread of the game. It now compiles them on its worker threads. The Vulkan
  driver also keeps its shader disk cache in one file, which makes a second start faster. In the bots demo on our
  BC-250, before the fix: 15 to 21 frames a second and the first frame after 77 to 101 s. With this release: 80 frames
  a second and the first frame after 21 s.
- **No scan-out in the first start after an install.** In the start of Windows between the end of the setup and the
  restart that the setup asks for, full-screen frames went through the desktop composition. The desktop driver now
  uses the default settings when its settings key is not there yet.
- **A GPU timeout soon after sign-in no longer counts that start as failed.** When the driver recovers from a GPU
  timeout in the first two minutes after sign-in, the start confirmation now waits longer. The known issue of
  tester.34 is gone.
- **Two restarts with no sign-in no longer switch the driver off.** A new task, "amdgpu-wddm startup confirm",
  confirms a start of Windows also when nobody signs in, for example after updates at night on a computer that does
  not sign in automatically. The known issue of tester.34 is gone.
- **Small, stretched desktop after the start.** When the board starts the screen in a small scaled mode (for
  example 800x600 on a 2560x1440 screen), the Display page of Nagi Control App now has the button "Use the full resolution".
  It sets Windows to start the screen in its highest mode (`bcdedit /set {globalsettings} highestmode on`), removes a
  fixed start resolution, keeps a backup for "Undo last action" and asks for a restart. The known issue of tester.34
  is gone.
- **llama.cpp from the setup did not install in tester.31 to tester.34.** The setup offered it, but those releases did
  not carry its file, so the download failed (HTTP 404) and the setup skipped it with a warning. This release carries
  its llama.cpp file, and the setup compares the SHA-256 of the file with the value in the package, as before.
- **After a restart with a high graphics clock, the clock control stayed off.** When Windows restarted less than 10 s
  after a game closed, or with a minimum clock above 1000 MHz, the driver read the next start as a crash and held
  the graphics clock at 1000 MHz. The driver now ends its clock session cleanly when Windows shuts down or restarts.
- **An update changed a graphics clock limit of 1500 MHz to 2000 MHz.** In earlier releases the setup set a graphics
  clock limit (`DpmMaxMHz`) of 1500 MHz to 2000 MHz on an update, because 1500 MHz was an old default. The setup now
  keeps a limit of 1500 MHz that you set, as it keeps every other value.
- **HIP: a wait for an event of a blocking stream now covers the default stream.** `hipEventSynchronize` and
  `hipEventQuery` on an event of a blocking stream could report it complete while work that the program issued on
  the default stream before the record still ran. They now wait for that work too, as the HIP rules for a blocking
  stream require.

## Known issues

- **A short temperature peak of about 90 C at a scene change:** when a game loads a scene at the full graphics clock
  of 2000 MHz, the chip temperature can rise from 84 C to 90 C in 2 s. The driver lowers the clock when the
  temperature goes above 87 C, and in that case it is 2 to 3 s late. The clock goes down to 800 MHz for about 20 s,
  then back up. The game continues. If your board gets hot, set the graphics clock limit to 1800 MHz in Nagi Control
  App. On our BC-250 the same scene change then reached 87 C. Rise of the Tomb Raider got a higher benchmark score
  than at 2000 MHz, because the clock stayed up for the rest of the run.
- **Update from tester.31 or tester.31v2 on Windows 11 24H2 or later:** until the update is complete, the old driver
  is still installed, and Windows Security can make the desktop flicker. The Smart App Control button of the setup
  window opens Windows Security. Before you start the setup, open PowerShell as administrator and run:

  ```powershell
  $k='HKLM:\SOFTWARE\amdgpu-wddm\AppRouter'; if (!(Test-Path $k)) { New-Item $k -Force | Out-Null }; $d=@((Get-ItemProperty $k -ErrorAction SilentlyContinue).Deny) + 'sechealthui.exe' | ? { $_ } | Select-Object -Unique; New-ItemProperty $k -Name Deny -PropertyType MultiString -Value $d -Force | Out-Null
  ```

  This adds Windows Security (`sechealthui.exe`) to the list of applications that always draw on the processor. It
  keeps the entries that are already in the list. It has an effect immediately, without a restart. An update from
  tester.31v3, tester.32, tester.33 or tester.34 does not need it.
- **A restart sometimes does not complete:** Windows shuts down, and then the screen stays black and the computer stays
  on. This can also occur at the restart that the setup asks for. On our BC-250 it occurred 3 times in about 70
  restarts on one day. The cause is not known, and it is not known if the driver causes it. Disconnect the power
  cable for about 10 seconds and start the computer again: Windows then starts normally, and an installation
  continues at the next logon.
- **Counter-Strike 2 sometimes stops drawing new frames** with no error, while the game still runs. On our BC-250 this
  occurred in 4 of 24 runs of the bots demo. Close the game and start it again.
- **Windows Terminal can lose its Direct3D 11 device a few times right after it starts.** Its window then stays
  without content for about 2 s each time and comes back by itself.
- A passive adapter that does not identify itself works only when it is connected at the start of Windows.
- Do not use hibernation: the first resume can crash Windows with `0x116`. Set the power button to "Shut down".
- **Some Direct3D 12 games stop for up to one second** while they compile shaders, also in places you visited
  before. Clair Obscur: Expedition 33 does this. We work on it.
- **This release does not offer Ollama.** An Ollama that you installed with an earlier release stays installed.
- **llama.cpp on HIP at the 12 GiB carve-out:** one run of Qwen3-8B Q8_0 stopped at its first prompt with
  `hipErrorUnknown`, because the code of one kernel did not get system memory. It did not occur again in later runs.
  If it occurs, start the program again.
- **A hang of the compute queue that the driver cannot stop** still stops Windows with `0x116`, as for a hang of the
  graphics queue.
- **A pixel shader that writes to memory at 8 or 16 samples** can also write for pixels at the edge of a triangle
  that the triangle does not cover. At 1 and 4 samples, and at sample frequency, it does not. Earlier releases also
  have this problem.
- **Direct3D 12 ignores ForcedSampleCount when a render target or a depth buffer is bound.** Earlier releases also have
  this problem.
- **Vulkan: the query counters of geometry shader primitives and of generated primitives read 0** on this graphics
  chip. The other pipeline statistics have their values.
- **Direct3D 12 stream output:** when a program draws a geometry shader stream 1, 2 or 3 and all its streams
  together need more than 8 clip and cull distances, that stream gets no clip or cull distance.
- **Indirect draws: the driver reports at most 4096 draws in one indirect draw call** (Vulkan
  `maxDrawIndirectCount`). The mesh shader path of this chip records each draw on the processor, so a higher limit
  would make each such call record all its draws, whatever its count.
- **When a Direct3D 12 game clears its driver cache**, the shared cache of the Vulkan driver
  (`%LOCALAPPDATA%\mesa_shader_cache`) stays. To clear it, remove that folder while no game runs.
- **32-bit Vulkan games:** VSync off stops only the wait for the desktop composition, because their picture goes
  through GDI, which cannot tear. The maximum frame latency has no effect there, because such a game can never
  queue more than one frame.
- **Game profiles: the driver reads only the options of each format that this route can use.** DXVK options of
  DXVK's own swap chain and of the adapter identity (for example `dxgi.customVendorId`, `dxgi.maxDeviceMemory`,
  `dxgi.enableHDR`) have no effect, because Windows' own DXGI does that work. A program name in a file must be
  exact, with the same upper and lower case letters. vkd3d-proton cannot name a program file whose name has
  letters outside ASCII.
- **A tool that reads AMD's identity data, for example a monitoring tool, can report the revision of a Radeon RX 6700
  series chip** instead of the revision of the BC-250. That is the identity that lets FSR 4 start. It does not change
  the graphics chip, its clocks or the driver. For a Direct3D 12 program, set "Allow FSR 4 in games that include it"
  to off for that program, and the program sees the revision of the BC-250.
- AMD's frame generation does not change: only the upscaler uses the new identity.

## Settings affected

- The installation keeps the settings that you changed.
- `LargePages` (DWORD) under `HKLM\SYSTEM\CurrentControlSet\Services\bc250kmd\Parameters`: the package default is now
  1 (large VRAM pages on). 0 turns them off. Set it with `bc250kmd_cli state set LargePages <value>`. The driver reads
  it when it starts. If you set it before, your value stays.
- New scheduled task "amdgpu-wddm startup confirm" (Local System, at the start of Windows). It confirms the start of
  the driver when nobody signs in. An uninstall removes it.
- "Use the full resolution" in Nagi Control App changes two boot settings of Windows only: `highestmode` and
  `graphicsresolution` in `{globalsettings}`. "Undo last action" sets them back.

## Tested

Host tests on the build computer, with no GPU, on the files of this release:

- Every component build of this release passed its host tests, 22 test programs with 0 failures: the Direct3D 11
  engine tests (243 cases) and the Direct3D 12 engine tests (222 cases), each for 64-bit and 32-bit programs, the
  tests of the per-game options, the shader cache size limit, the shader cache policy and the compile admission, and
  the Vulkan queue, submission and buffer lifetime tests (3108 test conditions).
- The HIP runtime tests had 3608 test conditions and 0 failures, also with the new kernel argument arena off. They
  include the GEMM tests of the hipBLAS library (550 test conditions).
- The files of this release hold none of the diagnostic setting names that a release build must not read.

Tests on a BC-250 with Windows 11:

- tester.34 was installed, and this release was installed over it without an uninstall. The setup reported
  `upgrading 0.7.216.106-tester.34 -> 0.7.216.107-tester.35`, the driver started after the restart, and the desktop
  used the graphics chip. Before the restart that the setup asks for and after it, the full-screen frames of a
  Direct3D 12 test program went to the screen directly, not through the desktop composition.
- With this release installed, llama.cpp from the setup ran at the rates of the table above (two runs of each row),
  at 1500 MHz with 40 graphics cores and the 12 GiB carve-out. Qwen3-8B Q8_0 had the same perplexity as before the
  package (11.4426) and answered "Paris" to a test question through its chat template. With the same llama.cpp and
  HIP files before the package, the llama.cpp backend tests passed 4894 of 4894 tests. The perplexity of each of the
  three models was that of a build with only the gfx1013 build patches, within the error range.
- With the lowest graphics clock fixed at 1500 MHz, Windows was restarted. In the next start the clock control was
  on, the idle clock went down to 500 MHz, and a lowest clock of 1500 MHz took the clock to 1500 MHz.
- Windows started the screen at 800x600 (`graphicsresolution` in the boot settings). "Use the full resolution" in
  Nagi Control App set the boot settings and kept a backup. After the restart the screen started at 1920x1200, and
  "Undo last action" put back the earlier values.
- Automatic sign-in was turned off and Windows was restarted. Nobody signed in, and the new task confirmed the start of
  the driver.
- The settings key of the desktop driver was removed and Windows was restarted: full-screen frames still went to the
  screen directly. With the key put back, the same.
- GPU timeouts were forced in the first minutes after sign-in. The driver recovered from each of them, and the start
  was confirmed. With adapter recovery turned off, a forced timeout stopped Windows with `0x116`, as it must. Windows
  started again with the desktop on the processor, as designed after a stop of Windows. "Reopen the GPU desktop path"
  of Nagi Control App and a restart put the desktop back on the graphics chip.
- With this release installed, a Direct3D 12 test program with the FSR 4.1.2 upscaler file of the AMD FidelityFX
  SDK 2.4.0 got FSR 4 with the switch on. Started with the program file name of a game on the anti-cheat list, it got
  FSR 3.1.6, also with a game program name of 20 characters.
- With this release installed and the hardware pointer on (the default), a camera saw the test pointer at the
  centre and at the lower right of the screen, and the driver log had the lines of the pointer. During 1250 mouse
  moves over the desktop, DWM made 2.1 frames per second. On the idle desktop it made 1.8.
- With this release installed, a Direct3D 12 test program got the application-specific driver state of the driver
  (132 bytes), and the driver used that state when the program gave it back. The driver ignored a state of random
  bytes.
- Counter-Strike 2 (Direct3D 11, in its default mode) played the bots demo to the end on a BC-250 with this release:
  80 frames a second (the count of the game: 81), the first frame after 21 s, and its full-screen frames went to the
  screen directly.
- Rise of the Tomb Raider (Direct3D 12) ran its built-in benchmark to the end on a BC-250 with this release: 90.73
  frames a second overall with the graphics clock limit at 1800 MHz (tester.34: 84.52 at 2000 MHz), with no GPU
  timeout and no stop of Windows. At the limit of 2000 MHz, two runs in a warm room got to 89 C at the first scene
  change of the benchmark, and our test rule stopped the game there (see "Known issues"). One run at 1800 MHz ended
  by itself 11 s after the start with an access violation in the game's own code, when Windows had 1.5 GB of memory
  free. The next run was complete.
- With this release installed, Quake II RTX ran its time demo with ray tracing pipelines (73.5 frames a second) and
  with ray queries (73.8 frames a second), and a full-screen game loop for 164 s, with no GPU fault, no GPU timeout
  and no device loss.
