# Nagi (amdgpu-wddm) 0.7.216.100-tester.29v2

A tester release of Nagi (amdgpu-wddm), an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and Nagi Control App of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes two records
that only this installer and this control program read.

The release before this one is 0.7.216.100-tester.29. This release replaces it. It is a second issue of tester.29
for a short test, and it carries the changes that we prepare for 0.7.216.100-tester.30. The notes of
0.7.216.100-tester.29 list the changes since 0.7.216.100-tester.28, and they apply to this release too, with the
changes below.

## How to install

Take one of the two downloads. The single file `amdgpu-wddm-setup-0.7.216.100-tester.29v2.exe` holds the whole
package: copy it to a local folder and double-click it. Or unpack the whole zip file to a local folder, then
double-click `setup.exe` in the folder it makes. The setup window asks for administrator rights itself. It reads the
state of the computer and shows what it will change. Your click on Install is your consent, and the window asks
nothing more. It restarts Windows by itself after a countdown of 15 seconds, and it continues after each logon. On
the command line, run `files\install.cmd` from the unpacked folder as administrator, with all its switches.
`INSTALL.md` in the package gives all ways.

- The kernel-mode driver is version 0.7.216.62.

## New

- **The installer asks you nothing after your click on Install.** There is no box to tick and no YES to type. When
  BitLocker is on, the installer pauses it for the restarts that it needs and tells you that it did. The uninstaller
  asks nothing either.

- **The release also comes as one file.** `amdgpu-wddm-setup-<version>.exe` unpacks the package into a folder that
  only administrators can write to. It tests every file and installs from there. It removes that folder when the
  installation ends.

- **The Microsoft Visual C++ runtime installs itself.** The driver's programs need the Microsoft Visual C++
  2015-2022 Redistributable (x64). The package now carries Microsoft's own installer for it. The installer runs it
  when the runtime is missing or older than 14.44. It tests the file's SHA-256 and its Microsoft signature first.
  This step needs no internet.

- **64-bit OpenGL programs run on the GPU.** This release has an OpenGL driver (ICD) for 64-bit programs. Windows
  loads it for every 64-bit OpenGL program, with no file beside the program. Until now Windows gave such a program
  its own software renderer, which is OpenGL 1.1. `verify.cmd` shows the line `OpenGL ICD`.

- **A notice at sign-in tells you when the graphics driver is not running.** When the driver's guard switched the
  driver off, the notice says so in plain words. Its button "Turn the graphics driver back on" starts the driver
  again without a restart of Windows. When the driver did not start for another reason, the notice opens Nagi
  Control App, which explains what happened. On a healthy computer you see no notice.

- **The small blue window after logon says what it is for.** Its two lines read
  `Nagi start check: confirming that the GPU driver started correctly.` and
  `Nothing to do. This window closes by itself in m:ss.` The time counts down to its close. In Nagi Control App, Settings, you can turn this window off. Read the warning next to that box before
  you do it.

- **The driver's name is Nagi.** The control application is now "Nagi Control App" and the setup window is
  "Nagi Setup". The installation puts "Nagi Control App" in the Start menu and on the desktop, and
  "Nagi Control App (recovery)" in the Start menu. An install over an older release removes the old
  "amdgpu-wddm Control" shortcuts, but only those that start our own program. The switches
  `-NoStartMenuShortcut` and `-NoDesktopShortcut` of `install.cmd` leave the shortcuts out. The files, folders,
  registry keys and tasks keep their technical name amdgpu-wddm.

- **The installer supports Windows 11 23H2, 24H2 and 25H2 and the general builds after them.** An older Windows 11
  gets a line that advises an update, and the installation continues. Windows 10 and older are refused.

- **A native Polish speaker read every Polish text of the setup window and of Nagi Control App.**

- **An install now gives all 40 graphics cores of the GPU.** The board's firmware switches on 24 of them, and
  every release until this one left it at 24. The game results that we publish are measured with all 40 cores. To
  keep the firmware's number, use `install.cmd -CuMode 24`, or select "Standard (24)" on the Graphics page of
  Nagi Control App. Both write the number 24 into the driver's settings, so a number that you choose yourself
  is kept by every later install. Where the driver itself went back to 24, the Graphics page says so and does
  not call that number your choice. The first start with 40 cores needs the confirmation of the small blue
  window after logon, as before. Without that confirmation the next
  start goes back to 24 cores and records why. An install and an upgrade keep that 24 and name it in the report,
  because the driver went back for a reason. `install.cmd -Repair` sets all 40 cores back, and so does "All (40)"
  on the Graphics page. All 40 cores use more power and make more heat than 24. The unlock's reference measured
  about 30 W more at 1500 MHz. That is a reference, not a promise for your computer.

- **The Nagi logo.** Nagi Control App and Nagi Setup show the Nagi logo beside their name, and a tip in each
  says what the name Nagi stands for.

- **The Nagi wallpaper.** After the installation is confirmed, Nagi Control App sets the Nagi wallpaper once for each
  person who signs in, and saves that person's previous background first. The setup window has a box for it next to
  the shortcuts, on by default, and `install.cmd -NoWallpaper` leaves it out. In Nagi Control App, Settings, "Nagi
  wallpaper" sets it again or restores your previous background. The uninstaller does not change your background.

- **Through a passive DisplayPort-to-HDMI adapter, you can now choose the screen mode, and the screen plays
  sound.** Up to this release the driver kept the one mode that the board set at power-on. It now offers the modes
  of the screen that the adapter can carry, changes to them and changes back. It also sends sound to the HDMI
  screen. A restart of the GPU device without a restart of Windows, for example from Device Manager, keeps the
  picture and the modes. On our test board, with an LG screen at 1920x1080 through such an adapter, these all gave
  a picture: 75 Hz, 60 Hz, 75 Hz again, 1280x720 at 60 Hz and back. A test tone came from the screen.

- **The window that Windows shows when a program wants to open a network port now draws on the processor.** That
  window is "Windows Security", with the Allow and Cancel buttons. On the last release it stayed white and empty,
  with only the program icon in it. It drew no text and no buttons, so there was nothing to answer. The program
  behind that window is `PickerHost.exe`, the File Picker UI Host. Windows uses the same program for the file open
  and save windows. This driver now gives that one program the processor driver instead of the adapter. It
  already does the same for the sign-in screens. Nothing changes for your other programs. This one program name is
  the whole change. You can put that program back on the adapter. Add `PickerHost.exe` to the `Allow` list
  under `HKLM\SOFTWARE\amdgpu-wddm\AppRouter`. That also helps us find the cause. To see the window at all, start
  a program that listens on a network port from a folder that has no firewall rule yet.

- **The Vulkan driver keeps one set of internal data for each adapter.** Up to this release it used one and
  the same slot for every adapter that is not reached through the desktop path. On a computer with a second AMD
  adapter the two could share that slot. The driver now names each slot by the adapter's own identifier, so each
  adapter gets its own. A computer with one adapter works as before. We have one adapter in our test board. Tests
  on a development PC cover this change, and no measurement on two adapters does.

## Fixed

- **The GPU starts on newer Windows builds again (Code 43).** Windows 11 24H2 and 25H2, and recent updates of
  23H2, refused the driver with code 43 ("Invalid user mode driver name", 0xC0000182). The installer left the
  first of the driver's file names empty, for Direct3D 9. It now writes `<>` there, which those builds accept.
  Direct3D 9 programs still go through D3D9On12 of Windows.

- **Windows 24H2 and 25H2 no longer stop with a blue screen (0x7E) when the driver starts.** The driver now keeps
  the copies of the screen that the Windows desktop makes in the part of VRAM that the processor can reach. Older
  Windows builds keep the placement that they had. The driver's tests on a development PC cover this change.

- **The desktop comes up on Windows 24H2 and 25H2.** There, the desktop (`dwm.exe`) stopped every 3 to 4 seconds
  with a stack overflow in the driver's desktop files. Windows calls them on a thread with a small stack, and the
  shader compiler needs more. The compiler of those files now runs on a stack that the driver owns.

- **Direct3D 9 games in a window no longer crash at their first picture.** A Direct3D 9 game reaches this driver
  through D3D9On12 of Windows. The driver refused the back buffer of such a game, and the game crashed. The driver
  now copies that picture into a surface of its own and shows the copy. On our test board, the 32-bit Unity game
  Poi, started with `-force-d3d9`, shows its title screen in a window and does not crash.

- **The setup window no longer draws texts over each other.** On a computer with no GPU driver yet, the two choices
  of where the files come from and the four language buttons showed two texts in one place. Each of these controls
  now paints its full area before its text.

- **The control application no longer keeps an old failed test in front of a newer result after Windows changes
  its clock.** Tests are ordered by Windows start and elapsed time. A failed test from before a restart is shown
  as a note when the installed driver is running now. A failed test of the current start still shows a problem.

- **The installer adds its certificate also when Windows refuses the usual way.** On a tester's computer the step
  stopped with "access denied" (0x80070005). The installer now tries `certutil` after such a refusal. It accepts
  the store only when the store holds the certificate.

- **An install right after an uninstall keeps its files over the next restart.** The uninstaller asks Windows to
  remove the files that are in use at the next restart. When you installed again before that restart, Windows
  then removed files of the new installation. The installer now takes each file that it is about to install off
  that list, before it copies the first file. Other entries in the list stay as they are. Setup tells you how many
  files it took off the list. No extra restart is needed between the uninstall and the install.

- **The installer no longer reports "the driver did not start" for a driver that runs.** After an install, the
  installer reads the state of the driver from Windows. It misread one form of the "no problem" answer. It then wrote a failure line and collected a diagnostic
  report for a healthy driver. It now reads that answer correctly. A real failure, such as code 43, still gives the
  failure line and the report.

- **The driver now starts when the firmware leaves the scaler in a state the driver did not expect (issue 38).**
  At start, the driver takes over the picture that the firmware left on the screen. It first reads how the
  firmware set up the path to the screen. Two fields of the automatic scaler can hold values while the automatic
  scaler is off. The driver read them anyway, refused the start, and Windows reported code 43 for the GPU. The
  driver now reads those two fields only when the automatic scaler is on. It reads the rest of the path as before.
  Our test board starts as before. The driver's tests now hold the case of issue 38, an 800x600 picture
  scaled to a 2560x1440 screen. We have no screen of that kind, so that case is not tried on real hardware. If your
  GPU still shows code 43 with this release, tell us in issue 38.

- **A language model through HIP now runs at the full GPU clock.** Up to this release the automatic clock control
  kept the GPU at the 1000 MHz base clock while llama.cpp generated text through our HIP runtime: the load of such
  a program did not reach the thresholds that graphics work reaches. The HIP runtime now tells the driver that its
  work is compute work. While a program of that kind runs, the driver uses lower thresholds, and the clock goes up
  to 2000 MHz. On our test board, Qwen3 1.7B (Q4_K_M) generated 62 tokens per second instead of 47 with the same
  llama.cpp files, and the GPU stayed under 71 C. Graphics and Vulkan programs are not affected.

- **After a GPU hang that the driver recovers, the driver is healthy again without a restart.** With the
  recovery of a hung GPU on (the default), the driver ended the hung work and the desktop came back. But the
  driver still reported its start as not healthy until the next Windows start, so the control program showed a
  problem that was gone. The driver now reopens its health record after a recovery. On our test board, one forced
  GPU hang was recovered, and one minute later the driver reported full health with the desktop on the GPU.

- **`bc250kmd_cli clock read` now answers without administrator rights (issue 7).** Up to this release the driver
  said "access denied" to a program that the person at the keyboard started. Such a program could show no clock,
  no voltage number and no temperature at all. The command now gives all three to any caller. Setting a clock with
  `bc250kmd_cli clock set` still needs an administrator window, as before. No number and no setting changes with
  this fix.

- **The game test runtime reads the temperature from the driver again.** It runs as the person at the keyboard, so
  the old refusal left it with no temperature, and it would not start a game. It now asks the driver first and
  falls back to the overlay. Every reading it writes down says which of the two answered.

- **An account without administrator rights keeps the driver now.** Until now the scheduled task that confirms a
  driver start ran only at the logon of an administrator. On a computer whose everyday account is a standard
  account nothing confirmed the start. After two restarts Windows went back to `Microsoft Basic Display Adapter`,
  and that user had no way to bring the driver back. The confirmation now runs at the logon of any user. Two
  scheduled tasks share the work. "amdgpu-wddm start confirm" runs as the Local System account and confirms the
  start. "amdgpu-wddm start window" runs as the user who logs on. It shows the small blue window that keeps the
  desktop drawing. The installer registers both. The uninstaller removes both.

- **Ray tracing could give a wrong picture when a shader ran out of registers.** A shader that needs more
  registers than the chip has parks some of its values in fast on-chip memory. It reads them back later. The
  compiler did not tell its own scheduler that a park and the matching read belong together. The scheduler could
  then move a read in front of the write that fills the same place, so the shader read an old value. In a Vulkan
  ray query test every ray missed the triangle it should have hit. The same fault can reach any compute shader
  that parks values this way, in the normal settings of the driver. The Vulkan and Direct3D parts of this release
  are built again with the fix. On our test board the failing case now passes. The full list of 140 ray tracing
  tests gives the same 137 passes as before.

- **The installation guide now says how many graphics cores an install gives you.** The guide said nothing about
  the number, and the switch `-CuMode` was only one name in a list. The section "What the installer changes" now
  holds the number of this release. It gives the switch `install.cmd -CuMode 24` for the firmware's number, and
  the same choice on the Graphics page of Nagi Control App. It also gives the rule that the first start with 40
  cores needs the confirmation of the small blue window after logon.

- **"Reset driver settings to the release defaults" set the graphics cores to 24.** The action in Nagi
  Control App took the firmware's number instead of the number of the installed release. It now sets the release's
  number, which is 40 in this release.

- **Resetting the driver settings in Nagi Control App no longer turns processor tuning off.** It now returns it
  to the release's setting, which is on.

- **The guide said the wrong highest GPU clock.** It still named 1500 MHz for a new install. The release default
  has been 2000 MHz since 0.7.216.100-tester.27. The guide now says 2000 MHz.

- **The driver log keeps 159 characters in a line.** Five of the summary lines that the driver writes at the end
  of a run were longer than that, so the last numbers of each line were cut off. One of them held the reasons why
  the driver refused to put a game's own picture on the screen. That is the first thing a support report needs for
  that problem. Each of these five lines is now two shorter lines, and no number is lost. The numbers themselves,
  the driver's behaviour and every setting stay as they were.

- **The driver can set the automatic GPU clock aside after a start that it must not repeat.** It now writes the
  reason for that act next to the setting (`DpmClosedReason`). It keeps the reason until somebody asks for the
  automatic clock again. Earlier releases lost the reason at the next start.

## Inside the driver

- **A test of the driver's paging engine runs again, and now runs on every build.** The test covers the step where
  the graphics engine stops a transfer at a safe point. The engine reports what finished, and it hands the
  unfinished work back to Windows. The test had stopped building months ago and nothing noticed, because no gate
  ran it. It builds and passes again, with 4256 single assertions. Four deliberately broken copies of the driver
  code prove that the test still fails when the driver is wrong. Nothing in this release changes for you because
  of it.

## Known issues

- This release is for a short test on our own board. We did not yet try it on Windows 24H2 and 25H2, and the fixes
  for those builds come from the driver's tests on a development PC.

- 32-bit OpenGL programs keep the software renderer of Windows, which is OpenGL 1.1. This release has no 32-bit
  OpenGL driver. 32-bit Direct3D programs are not affected.

- Read without an administrator window, the three clock numbers are the driver's last reading. They can be up to
  one second old. The driver takes a fresh reading when the last one is older than that. Read from an
  administrator window, the numbers come from the chip at that moment, as before. This is what keeps many programs
  asking at once from adding work on the chip. However many ask, the driver reads the chip no more often than it
  reads it for itself.

- The version of the driver does not tell you whether your driver answers an ordinary user. The command does. Run
  `bc250kmd_cli clock read` in an ordinary window. It either prints the numbers or it says access denied. Note
  also that 0.7.216.100-tester.28 and 0.7.216.100-tester.29 dropped the known issue about this refusal from their
  notes although the fix had not shipped. Both of those releases still refuse an ordinary user. This release is
  the first that does not.

- The small blue window now stays for the full two minutes at every logon. Earlier releases closed it as soon as
  the start was confirmed, normally after about one minute, because one task did both halves of the work. The two
  tasks are independent, and the window does not read the confirmation's progress. Do not close the window. It
  closes itself. Where the window does not run at all, for example at a logon that ends at once, the confirmation
  still keeps the computer off `Microsoft Basic Display Adapter`. The next start then runs at the fixed 1000 MHz
  clock until you confirm the automatic clock control again.

- An install gives all 40 graphics cores in this version, so a computer that ran 24 cores under an earlier
  release changes its number at this upgrade, unless you chose 24 yourself. There is a third case: an earlier
  driver that went back to 24 by itself left no record of that step. This install keeps that 24 and reports it
  as your own number. Run `install.cmd -Repair`, or select "All (40)" on the Graphics page, to get all 40 cores
  on such a computer. More cores use more power and make more heat. Make sure the case has good air flow.

- A program that draws on the processor gets the Direct3D feature level 10_0 from this driver. That is the known
  limit of the processor route. A window of this kind should not need more. If a file open or save window stops
  appearing after this release, put `PickerHost.exe` in the `Allow` list and tell us. That undoes the change for
  that one program. We moved the route and we did not make the drawing work. We do not yet know why that window
  did not draw on the adapter.

- **The desktop files of the driver still build their shaders at every start.** The files that draw the Windows
  desktop are `desktop\amdgpu_wddm_radv.dll` and `desktop\bc250d3d_zink.dll`. They keep nothing on disk, so they
  do the same work again every time Windows starts. The Vulkan file and the Direct3D files that games use do keep
  their work on disk, and they are not affected. The desktop runs under an account of Windows that has no folder
  of its own for such a store, so the fix needs more than a rebuild. We will fix it in a later release.

- A support report from this version holds more log lines than one from an earlier release, because five lines
  became ten. The log keeps the same number of lines in total, so a very long run now wraps a little earlier.

- **HDMI through a passive adapter: we tested one screen through one adapter.** We did not change the adapter or
  the cable while Windows ran, and we did not connect a DisplayPort screen directly with this release. After a
  change of the cable, restart Windows. For the sound, we listened to one test tone. Three automatic tests of the
  sound path stay open: sound at 44.1 kHz, the playback position, and how Windows puts the sound device
  together with the screen.

- The known issues of 0.7.216.100-tester.29 apply, except the two that this release fixes: an account without
  administrator rights now keeps the driver, and a screen through a passive HDMI adapter now has more than one
  mode.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.

- `UserModeDriverName` and `UserModeDriverNameWow` start with `<>` instead of an empty entry. That entry is the
  slot of Direct3D 9.

- `OpenGLDriverName`, `OpenGLVersion` and `OpenGLFlags` on the GPU's software key register the 64-bit OpenGL
  driver. The uninstaller removes them. This release writes no 32-bit OpenGL value.

- `ShowStartWindow` under `HKCU\Software\amdgpu-wddm\Control`, for each account: `0` turns the small blue window
  off for that account. No value, or any other value, shows it. The sign-in notice does not depend on it.

- `CuMode` is new in the installer's own table and gets 40. The driver writes `CuModeClosedReason` next to a 24
  that it wrote itself, which is how the installer tells its own fallback from a number that you chose. A `CuMode`
  of your own is kept, and the record goes as soon as anybody asks for the cores again.

- Two scheduled tasks instead of one: "amdgpu-wddm start confirm" as the Local System account, and "amdgpu-wddm
  start window" as the user who logs on. The installer registers both, and the uninstaller removes both.

- `C:\ProgramData\amdgpu-wddm\start-confirm.log` now ends each logon with what the window task did. It names the
  task's state, its last run time and its last result. A result of `0` means the window was shown and closed. A
  result of `2` means it could not be shown. A result of `3` means you turned the window off.

- `Allow` and `Deny` under `HKLM\SOFTWARE\amdgpu-wddm\AppRouter` keep their meaning. `Allow` now also lifts the
  driver's own built-in list. `Mode` `allowlist` is unchanged. Every program that is not in `Allow` stays on the
  processor there, as before. The route change needs no registry value and no extra restart.

- `DpmMaxMHz`, `SubmitWatchdogMs`, `FanLoadBoost`, `EnableDpAudioContainerId`, `HangRecoveryWaves`,
  `EnableRingVmFlush` and `TdrDelay` stay as 0.7.216.100-tester.29 set them.

## If something goes wrong

- When the driver does not start, send us the text file that the installer names at the end of its run, or the
  support file of the setup window, which holds the same text.

- When the sign-in notice says that the graphics driver was switched off, make a support report first if you want
  us to see why. The button "Turn the graphics driver back on" clears the count that the driver kept.

- If a game loses its picture or shows the wrong picture with ray tracing on, and it did not do this with the
  earlier release, tell us. The compiler fix of this release touches every shader that parks values in on-chip
  memory.

- If the small blue window does not appear at the logon of a standard account, send us
  `C:\ProgramData\amdgpu-wddm\start-confirm.log`. Its last line of each logon names what the window task did.

- Look at the preview of a support file before you send it. When you find personal data in it, do not send the
  file, and tell us in the report so that we can fix the application.

- Send us the support report from Nagi Control App. It holds the driver log and the stored graphics settings.
