# amdgpu-wddm 0.7.208.100-tester.13

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and amdgpu-wddm Control of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes a record that
only this installer and this control program read.

## New

- The kernel-mode driver is version 0.7.208.1.
- Ray tracing is on for every Direct3D 12 game. The release before this one reported ray tracing to The Witcher 3
  only. Other games that offer ray tracing can find it now. We measured ray tracing in The Witcher 3 only, so
  another game can be slow with it, or can draw wrong. The Games page of amdgpu-wddm Control has a box for ray
  tracing support. Clear the box for one game, and that game gets no ray tracing.
- The graphics libraries for Direct3D 11 and Direct3D 12 use a new build of the Vulkan driver (Mesa RADV). The build
  keeps the shader disk cache, so a game compiles its shaders again only after a change of the driver. The release
  before this one kept the older build, because the newer one made the GPU write to an invalid address in a program
  that uses WebView2. We found the cause in the key of the shader cache, and we made it cover the whole shader state
  again.
- The Direct3D 11 path and the Direct3D 12 path use the same build of the Vulkan driver. A program that uses both of
  these interfaces therefore compiles each shader one time, and both paths read the same shader disk cache. The
  package holds a copy of that build for each of the two paths.
- 32-bit programs get a Direct3D 11 driver and a Vulkan driver from the same sources as the 64-bit ones. Every 32-bit
  file of this package comes from a commit of our repository now. No file needs a patch any more.
- The H.264 video encoder takes an NV12 texture from a program. Before, it took a BGRA texture only. A program that
  holds its frames in NV12 therefore needs no colour change before the encoder.
- The driver log says more about the direct screen path. One line counts the images that the driver put on the
  screen. One line counts the images that it refused, and it has a column for each reason. A support report
  therefore says why a game did not get the direct path.
- amdgpu-wddm Control is version 0.5.1.0. It reads the last run of the driver start task from two sources in Windows,
  and it takes the newer of the two answers.
- The Recent page of amdgpu-wddm Control lists the games and the programs that used the Direct3D 12 driver. That page
  was empty in every release before this one.
- The Direct3D 12 driver records a command list through a shorter path. We measured 3.8 % more frames in The Witcher
  3 at the low preset with it. The name `direct-entry-off` turns the shorter path off for one game.
- Three more behaviours of the Direct3D 12 driver apply to every program now. The release before this one gave them to
  The Witcher 3 only. They are the recording entry of a command list, the hand-off of the release sequence to the
  resource calls, and the record and replay of the recording calls on a worker thread. `recording-bind-off`,
  `retire-handoff-off` and `deferred-replay-off` turn them off again, for one program or for the machine.

## Fixed

- The desktop driver lost memory for each window surface that it could not set up at the first try. It continues the
  setup now. Both desktop routes have this change: the route that draws with the processor, and the route that draws
  with the GPU.
- The desktop driver refused a one-byte-per-pixel image as a composed surface. It accepts that image now. The kernel
  driver accepted it from the release before this one, so the two halves are in one release at last.
- A Direct3D 12 program that asked for a shared resource could lose its graphics device, and Windows then stopped the
  driver. The driver refuses such a resource with an out-of-memory answer now, and the device stays alive. A program
  that reads the answer continues to run. A shared resource between two programs still does not work.
- The Direct3D 12 driver could not import a heap while another thread held the ownership of the memory. It retries
  the unlock now.
- ClearRootArguments wrote nothing. The Direct3D 12 driver records the real values now, so a root descriptor keeps
  its value after that call.
- The Direct3D 11 driver gave Windows a status that the interface does not allow at 99 places. A gate of our build
  holds the rule for each of those answers now.
- An installation could not tell a driver fall-back from a value that the tester set. The kernel driver writes the
  reason it turned the automatic GPU clock off, and that record outlives the restart. `install.cmd -Repair` writes
  the automatic clock back and removes the record. Every other installation keeps the value, and it names the
  fall-back in its report. The Recovery page of amdgpu-wddm Control offers the way back one boot or more after the
  fall-back.
- The Vulkan driver read a settings file from a folder that every user can write, and it wrote a log into a shared
  folder. The Direct3D 12 driver read the same file, and it wrote its measurement log into the same folder. Neither of
  the two drivers does this now. A measurement setting comes from the environment of the program that gets it.
- The Direct3D 12 driver turned sparse binding off when it could not read the value `AmdgpuWddmSparseBinding` of the
  adapter key. It then also lost feature level 12_1 and tiled resources tier 3, and it said nothing about it. Only the
  value 0 turns sparse binding off now. The driver writes a log line for each other answer.
- The driver profile of The Witcher 3 held six switch names. Four of them are the behaviour of the driver now, and
  the driver reads those four names and does nothing with them. The installer writes the two names that are still
  switches.

## Known issues

- The Vulkan driver for 64-bit Vulkan programs is the build of 2026-09-27, as in the two releases before this one. It
  copies each frame through the processor, and it has no shader disk cache. 32-bit Vulkan programs get the new build.
  We keep the older 64-bit build, because it holds screen work that the new build does not have yet. Direct3D 11 and
  Direct3D 12 programs are not affected: they get the new build.
- The Direct3D 11 path of this release is new in every part. If a Direct3D 11 game does not start, or draws wrong,
  send us the support report. The release before this one is the way back.
- We did not test a program with the H.264 encoder on the BC-250. We tested the encoder itself, with our own test
  programs, for BGRA input and for NV12 input.
- The encoder tells Windows two things: that it is a hardware encoder, and that it gives its frames back
  asynchronously. Windows can therefore give the encoder to a program that asks for any asynchronous encoder. It does
  not give it only to a program that asks for a hardware encoder. If a program records worse video than before, or
  does not record at all, send us the support report. We can make a release that does not install the encoder.
- If you install an older release over this one, the registry keys of the encoder stay. Only the uninstaller, or a
  later release without the encoder, removes them.
- The direct screen path is for a game in fullscreen or borderless mode. The desktop compositor decides for a
  borderless window, so the path is not sure there.
- After a crash or a power loss the driver closes the GPU desktop path, and the processor draws the desktop (slower
  animations). "Reopen the GPU desktop path" on the Recovery page of amdgpu-wddm Control opens it again.
- Some programs that use WinUI or XAML do not draw their window content on the GPU. Windows apps are not affected,
  because they use the processor.
- 32-bit Direct3D 12 programs do not have a driver yet.
- Secure Boot must be off, and Windows runs in test mode, because we sign the driver with a test certificate. The
  desktop then has the words "Test Mode" in its corner.
- The installation needs internet access for the AMD GPU firmware, or a folder with the firmware files
  (`INSTALL.md`, section "GPU firmware").
- The Microsoft Visual C++ 2015-2022 Redistributable (x64) must be installed.
- After each logon, a small blue window confirms the driver start for about one minute. Do not close it.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.
- The installer lists each setting it changes before it changes anything.
- This release adds no driver setting. `EnableScanoutAdmit` and `DpmIdleMHz` of the release before this one keep
  their meaning and their defaults.
- The driver profile of The Witcher 3 goes from six names to two: `present-noprimary` and `present-cached`. The
  installer writes the new value, and it lists the change.
- An administrator can turn one behaviour of the Direct3D 12 driver off for one program. Set the value `Experiment`
  under `HKLM\SOFTWARE\amdgpu-wddm\D3D12\Applications\<program file name>` to one name, or to several names with a
  comma between them. Each name of this kind ends in `-off`. The same value under `HKLM\SOFTWARE\amdgpu-wddm\D3D12`
  turns a behaviour off for every program. If a Direct3D 12 game behaves worse than before, try these five names in
  this order: `raytracing-tier-off`, `direct-entry-off`, `deferred-replay-off`, `recording-bind-off` and
  `retire-handoff-off`. The name `replay-log` changes no behaviour: it writes a log of the recording work for a
  support report.
- The value `AmdgpuWddmSparseBinding` of the adapter key keeps its meaning and its default. Only the value 0 turns
  sparse binding off now, where an unreadable value did so before.
