# Nagi (amdgpu-wddm) 0.7.216.102-tester.31

A tester release of Nagi (amdgpu-wddm), an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and Nagi Control App of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes two records
that only this installer and this control program read.

The release before this one is 0.7.216.101-tester.30. This release replaces it. The notes of
0.7.216.101-tester.30 list the changes since 0.7.216.100-tester.29v2, and they apply to this release too, with the
changes below.

This release has two flavours from the same source line:

- **Release** is the package for normal testing. It excludes raw kernel diagnostics and shader overrides.
- **Lab** keeps those diagnostics for driver development and fault investigation. Its download names end in
  `-lab`. Use it when a diagnostic procedure specifically asks for it.

Both flavours are signed with our **test certificate** and still require Windows test-signing mode. The release
flavour prepares the driver files and submission CAB for Microsoft attestation. It is not Microsoft-signed and
has not passed HLK certification. Buying an EV certificate does not itself sign or certify this package.
The user-mode driver files are installed through the driver package into the Windows DriverStore.

## How to install

Choose the release flavour unless you need the lab diagnostics. The single file `amdgpu-wddm-setup-0.7.216.102-tester.31.exe` holds the whole
package: copy it to a local folder and double-click it. Or unpack the whole zip file to a local folder, then
double-click `setup.exe` in the folder it makes. The setup window asks for administrator rights itself. It reads the
state of the computer and shows what it will change. Your click on Install is your consent, and the window asks
nothing more. It restarts Windows by itself after a countdown of 15 seconds, and it continues after each logon. On
the command line, run `files\install.cmd` from the unpacked folder as administrator, with all its switches.
`INSTALL.md` in the package gives all ways.

- The product version is 0.7.216.102-tester.31. Windows reports its driver package version as 40.7.216.102.
  The package manifest records the build and identity of each component. Keep the files of each flavour together.

## New

- **Nagi Control App can write a log file for a game.** A game or program that does not work as you expect can now
  be recorded. You turn the switch on in Nagi Control App, you start the game, and the driver writes what it does
  into a file for you to send us. The switch runs for a time that you choose and then stops by itself, so a log
  cannot fill your disk: each file stops at 64 megabytes, and every program that starts while the switch is on
  gets a file of its own. "Stop now" ends the recording at once. The Direct3D 11, Direct3D 12 and Vulkan drivers
  all write into these files.

- **The driver now starts with 24 of the 40 graphics cores, and you choose how many to use.** 24 is the number
  that the firmware of the board switches on by itself. The Graphics page of Nagi Control App selects any number
  from 24 to 40 in steps of two. It can also map the pairs of cores one by one, so a pair that makes the computer
  unstable can stay off.

- **A DirectX 12 game that builds its shaders while it loads now loads faster.** Such a game asks the driver for
  one pipeline after another, and each one holds a shader to compile. The driver compiled them one at a time, on
  the thread of the game that asked. It now compiles them on all the cores of the processor but one, and the game
  goes on while they are built. On our board the first load of Death Stranding fell from 498 seconds to between
  308 and 368. A game that needs a pipeline at once still waits for that one pipeline, so nothing is ever drawn
  with a shader that is not ready. "If something goes wrong" below says how to turn this off for one game or for
  every program.

## Fixed

- **The driver activates its saved device state when Windows starts the device.** An earlier tester.31 candidate
  tried to activate that state while Windows was still adding the device. An upgrade from tester.30 could then
  fail before the driver started, with Code 31 and status `0xC000014D`. Device addition now prepares the state,
  and device start activates it. The shared-state reader also requests the service configuration access it needs.

- **The installer keeps its DriverStore directory paths separate.** An earlier candidate joined three directory
  names into one path, so the driver-package installation could fail before the new driver was selected.

- **The desktop now appears when the firmware starts the screen in a scaled mode.** Some boards leave a small
  picture stretched to the full size of the screen when Windows starts, for example a picture of 800 by 600 on a
  screen of 2560 by 1440. The driver refused the plan that Windows inherited from the firmware in that state, so
  the screen stayed on the Windows logo, and the third start in a row was refused by the safety rule of the driver.
  The driver now reads the geometry of the output, accepts the inherited plan, and keeps the native mode as the
  fallback. It also starts a board whose inherited picture runs above 300 megahertz, which it refused before, and
  a start that is refused all the same now undoes its own preparation, so the next start finds a clean
  state. Checked on our board at 800 by 600, at 1024 by 768 and at the native mode of the screen. (GitHub issue 38)
  Note: while the screen is started that way, the driver shows only the mode it inherited. The desktop is a small
  picture stretched to the full size of the screen, and Windows lists that one mode. Set the picture of the
  firmware to the native mode of the screen to get the full size back. If a Windows setting holds the small picture
  instead, open a command prompt as an administrator, run `bcdedit /deletevalue {globalsettings}
  graphicsresolution`, and restart the computer. The driver work that asks the screen for its own mode in this
  state is in development, and this release does not promise it.

- **The whole desktop no longer becomes slow while the Epic Games Launcher is visible.** With that window open the
  taskbar answered a message in about 50 milliseconds instead of 0.6, and the desktop drew only about 20 times a
  second, with the GPU almost idle. Windows copies the picture of such a window through a surface that the
  processor reads every frame, and that surface was in a memory that the processor reads slowly. It is now in the
  memory that is fast for the processor. On our board the measured answer of the taskbar with the launcher visible
  fell from 49.3 to 0.9 milliseconds. (GitHub issue 41)

- **The Direct3D 11 driver now offers only the driver interface that the graphics adapter supports.** It offered a
  newer one than the adapter reports, which the Windows compatibility tests refuse at every feature level, and
  which made one Direct3D 9 test fail to create its device. The controls of 0.7.216.100-tester.24 for the vertical
  synchronisation keep working as before.

- **The support report of Nagi Control App now holds every crash record of the last 24 hours.** It kept only the
  records whose text names a part of the graphics stack, so a game that closed itself in its own code left no
  record in the report, and a report about "the game does not start" held nothing to read. The report now keeps
  every Application Error, Application Hang and Windows Error Reporting record of the last 24 hours, newest first
  and at most 500 of them.

- **The driver package no longer carries a restart directive that Windows refuses for a graphics driver.** The
  installer asks Windows to stage the driver set and to bind it at the restart, which it does itself after the
  countdown, so the installation works as before. The package now passes the Windows driver package check. The
  installer also writes a receipt of the step that put the driver on the GPU.

- **The command-line tool writes each measurement at once.** `bc250kmd_cli dpm`, `telemetry` and `fan` write a
  line for every sample. Sent to a file, they wrote nothing until the program ended, so a program that watched the
  temperature from that file saw no line at the start of a run, or a hot sample late.

- **The installed driver reports the version number that games read, and you set nothing for it.** Windows records
  this driver under a number in the AMD style, 40.7.216.102 for release 0.7.216.102, because some games refuse to
  run on an older AMD driver version. The number comes with the package, there is no setting to turn on, and the
  last step of the installer reads the number back from the installed driver and writes it in one line.

- **Nagi Control App starts the right Quake II RTX.** The benchmark page asked Steam for the program number of
  the old demo, so the benchmark did not start on a computer with the game from Steam. It now asks for the number
  of Quake II RTX itself.

- **"Render on CPU" says what it can and cannot do.** The text of that setting promised more than the setting
  gives: the processor path does not offer all of DirectX 11, and most games made after 2012, Counter-Strike 2
  among them, do not start with it. The help text and the note beside the setting now say so, in all four
  languages.

- **The setup program no longer leaves an empty folder of its own behind.** The single file that installs this
  driver unpacks itself into a folder under `C:\ProgramData`, and that folder stayed on the disk after the run,
  empty and removable only by an administrator. The setup program now takes its folder away again when it is
  finished with it.

## Known issues

- **After a crash or power loss, the desktop can stay on the CPU and automatic GPU clocks can stay off.** The
  driver closes these paths after an unclean end to avoid repeating it. The combined Home-page notice and recovery
  action for this state (BD-181) are not included yet. Open Nagi Control App, choose "Reopen the GPU desktop path"
  on the Recovery page, and restore automatic clocks on the Performance page if they are off. Restart Windows to
  apply those settings. `INSTALL.md` also describes `install.cmd -Repair`, which reopens the driver's closures.
  If the paths close again, send a support report instead of repeatedly reopening them. The notice and combined
  recovery action are planned for tester.32. The existing safety checks and separate recovery controls remain.

- The known issues of 0.7.216.101-tester.30 apply, the missing power numbers on a board with the 8-core processor
  unlock among them.

- **Counter-Strike 2 compatibility in its default Steam mode remains unverified.** Earlier tests encountered
  graphics-module trust checks and a DirectX 11 renderer that produced no picture. The DriverStore layout and test
  signatures do not establish that those problems are resolved. Keep the game's normal trust settings.

- **3DMark Time Spy can hang the GPU and crash Windows with `VIDEO_TDR_FAILURE` (`0x116`).** This remains open
  as BD-180. The shader and submission fixes made during the investigation have not produced a completed benchmark.
  There is no accepted workaround. Time Spy is a known exception for this release, and investigation continues
  after publication. Do not treat it as a passing stability test of this package.

- **Games protected by BattlEye do not start while the test mode of Windows is on.** BattlEye stops with the
  message "Failed to initialize BattlEye Service: Windows Test-Signing Mode not supported", so the game closes
  before it opens. We measured it with War Thunder: four starts from Steam, all the same, and the game's own
  program never ran. Starting the BattlEye service by hand does not help, because its client stops the service
  again. Both flavours of tester.31 still require test mode. Compatibility after Microsoft signing has not been
  measured. We measured no other anti-cheat system, so we claim nothing about them.

- The game log is new. Tell us when a log file stays empty, when the switch does not stop by itself, or when a game
  becomes slow while the switch is on.

- **On some screens the driver still does not start, and Device Manager shows Code 43.** At its start the driver
  reads the picture that the firmware of the board left on the screen. On some combinations of board and screen it
  cannot tell what the firmware programmed, so it refuses to start instead of guessing, and Windows falls back to
  its own basic graphics driver. The screen keeps a picture, because the firmware's output still runs, but no game
  and no feature of this driver is available. To tell this apart from another failed start, open
  `HKLM\SYSTEM\CurrentControlSet\Services\bc250kmd\Parameters\StartRecord`: `Result` is `failed`, `Step` names the
  check of the screen that refused, `Status` is its code, and `Detail` holds the numbers the driver read. Send us the
  support report of Nagi Control App, which carries that record, the driver log of the failed start and the
  identification of the screen. We know of no workaround: a lower refresh rate does not reliably help, because the
  refusal does not depend on the pixel clock, and a restart programs the same picture again. Two causes are gone in
  this release (see the first fix above). The route that takes the screen over instead of refusing, by stopping the
  firmware's output and programming a mode from the screen's own data, is being worked on. We promise no release
  for it here.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.

- **An upgrade from 0.7.216.101-tester.30 sets the number of graphics cores back to 24, once.**
  0.7.216.101-tester.30 could not record that you had chosen 40 yourself, so this install cannot tell your choice
  from its own default. Choose your number again after this install. From this release on, every upgrade keeps it.

- This release changes one default. `CuMode` is 24, where 0.7.216.101-tester.30 wrote 40. `DpmMaxMHz`,
  `SubmitWatchdogMs`, `FanLoadBoost`, `EnableDpAudioContainerId`, `HangRecoveryWaves`, `EnableRingVmFlush` and
  `TdrDelay` stay as 0.7.216.101-tester.30 set them. The game log is off until you turn it on, and it turns itself
  off again.

- The release flavour no longer reads `MESA_SHADER_CACHE_DIR` or `MESA_GLSL_CACHE_DIR`. Its shader cache stays in
  the default folder, `%LOCALAPPDATA%\mesa_shader_cache`. The lab flavour retains diagnostic overrides.

- `AMDGPU_WDDM_D3D12_EXPERIMENT` and `AMDGPU_WDDM_D3D11_EXPERIMENT` have no effect in the release flavour. Earlier
  notes told you to set them for one game. For a Direct3D 12 game, use the switches of its profile on the Games page of Nagi Control App.
  For a Direct3D 11 program, put the same text in the `Experiment` value under
  `HKLM\SOFTWARE\amdgpu-wddm\D3D11\Applications\<program>.exe`.

- `BC250_HIP_GPU_COPY` has no effect now: a copy from the card to the computer always runs on the graphics
  cores. The `=0` setting of the 0.7.216.99-tester.28 notes was the other side of that measurement, not a
  workaround. The one fault that the new route showed, a buffer that starts where another one ends being
  missed, was fixed in 0.7.216.99-tester.28. If a model gives wrong answers, send us a support file.

- "Record game logs" no longer records OpenGL programs: the OpenGL driver of this package writes no log. For a
  problem in an OpenGL program, send us a support file instead.

- From this release, a 32-bit Vulkan program ignores `MemoryOverflow`, which is what a 64-bit one already did.
  Direct3D 11 and Direct3D 12 programs still honour it.

## If something goes wrong

- When the driver does not start, send us the text file that the installer names at the end of its run, or the
  support file of the setup window, which holds the same text.

- When the screen stays black or shows the Windows logo after the installation, tell us which screen and which
  resolution the firmware of the board uses. The fix of this release reads the geometry of the output.

- When a DirectX 12 game starts badly, draws wrongly or stops while it loads, you can ask the driver to build the
  shaders of that game one at a time, as the releases before this one did. Write `async-pso-off` into the value
  `Experiment` of the registry key `HKLM\SOFTWARE\amdgpu-wddm\D3D12\Applications\<name of the program>.exe` for
  that one game, or of `HKLM\SOFTWARE\amdgpu-wddm\D3D12` for every program. Start the game again, and tell us what
  happened.

- Look at the preview of a support file before you send it. When you find personal data in it, do not send the
  file, and tell us in the report so that we can fix the application.
