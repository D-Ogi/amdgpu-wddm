# Nagi (amdgpu-wddm) 0.7.216.108-tester.36

A tester release of Nagi (amdgpu-wddm), an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It
replaces 0.7.216.107-tester.35.

It is signed with our **test certificate** and still requires Windows test-signing mode.

## How to install

Copy `amdgpu-wddm-setup-0.7.216.108-tester.36.exe` to a local folder and double-click it. Or unpack the zip file
and double-click `setup.exe` in the folder it makes. You can install this release over tester.31, tester.31v2,
tester.31v3, tester.32, tester.33, tester.34 or tester.35: you do not have to uninstall first. The setup updates the
installed release and keeps the settings that you changed. Before an update from tester.31 or tester.31v2 on
Windows 11 24H2 or later, read the known issue about that update. Windows reports the driver package version as
40.7.216.108, which is higher than the version of each of these releases.

## New

- **Experimental: PyTorch from AMD's TheRock packages on our HIP runtime.** The package has a new folder,
  `tools\hip\rocm`, for the Python packages `rocm-sdk-core` and `rocm-sdk-libraries` 10.3.0a20261030 of AMD's
  TheRock build for gfx1010. It holds our `amdhip64_7.dll`, our `libhipblaslt.dll` (it adds the 8-bit integer
  matrix product that `torch._int_mm` needs) and the step that puts both into a Python environment (venv). Run it
  once for each venv, with no Python of that venv open:

  ```
  powershell -ExecutionPolicy Bypass -File "C:\Program Files\amdgpu-wddm\tools\hip\rocm\attach-rocm-venv.ps1" -Venv C:\path\to\venv
  ```

  The step keeps AMD's two DLLs in the venv and refuses a venv of another TheRock build. `-Check` reports the state
  of a venv, and `-Detach` puts AMD's DLLs back. The folder is not on PATH, so no other program loads these DLLs.
  The Graphics page of Nagi Control App also has a card for this step.
- **HIP: one allocation can now be larger than 4 GiB.** The runtime makes such an allocation from parts in the
  graphics memory. Before, the driver refused one allocation of about 7 GB at the 8 GiB carve-out, so a dense 12B
  model could not load on HIP (BD-117). On our BC-250 at the 12 GiB carve-out, PyTorch got one buffer of 11.48 GB in
  graphics memory, and its kernels read all of it with no error. At the 8 GiB carve-out, an allocation of 6 GiB worked,
  and a request that is larger than the free memory gets an out-of-memory error.
- **Image edits with Qwen-Image 2.1 in ComfyUI work on the BC-250.** Use at least 12 steps. At 4 steps with cfg 1.0,
  the picture looks like a double exposure. That is too few steps for this model, not a fault of the runtime. On
  the 8 GiB carve-out, one step takes about 52 s.
- **OpenCL through Microsoft's Compatibility Pack.** The driver has no OpenCL driver of its own. Install the
  "OpenCL, OpenGL, and Vulkan Compatibility Pack" of Microsoft, and OpenCL programs get the device "BC-250 GPU
  (amdgpu-wddm)" through our Direct3D 12 driver. Our OpenCL test program got the expected results for 1048576
  values. The pack also adds a Vulkan driver of Microsoft. (BD-083, GitHub #18)
- **Vulkan: one memory heap for the graphics memory.** On this chip the graphics memory and the system memory
  are the same memory. For 64-bit programs, the Vulkan driver now reports them as one device-local heap: about
  11.3 GiB at the 8 GiB carve-out, in place of two heaps of 7.6 GiB and 3.8 GiB. Programs that size their memory
  pools from the Vulkan heaps can now use more of the memory. 32-bit programs keep the two heaps.
- **More graphics memory for programs.** The driver keeps less memory for its page tables: 64 MiB in place of
  247 MiB at the 8 GiB carve-out.
- **Windows gets the name and the memory size of the graphics adapter.** The driver now writes the adapter
  information values into its registry key. Before, tools that read these values reported "Microsoft Basic Display
  Adapter" and no memory size. (BD-245)
- **Screen capture and recording are tested on the GPU desktop.** Desktop Duplication and Windows.Graphics.Capture
  (for an application window and for the full screen) work when the desktop draws on the graphics chip. (BD-084,
  GitHub #20)

## Fixed

- **No short temperature peak of 90 C at a scene change.** Two new rules lower the graphics clock before the
  temperature gets to 87 C. The first rule acts when the temperature is 80 C or more and goes up by 1.5 C a second
  or faster. The second rule steps the clock down to 1800 MHz when the temperature is 80 C or more. In the
  benchmark of Rise of the Tomb Raider at 2000 MHz on our BC-250, the temperature peak was 87-88 C, and the
  benchmark ran to the end. With tester.35, it got to 89-91 C. The known issue of tester.35 is gone. (BD-281)
- **Windows could stop while the desktop drew on the processor.** When the desktop drew on the processor, for
  example after a GPU timeout, two copies of a picture to the screen at the same time could release the memory
  view of the other copy. Windows then stopped with `0x0A` or `0x50`. The copies to the screen now wait for each
  other. (BD-289)
- **Programs no longer stop responding when the graphics adapter stops.** A restart of the graphics device (for
  example a change of the graphics core count in Nagi Control App) or a disconnected and connected HDMI cable could
  make Explorer stop responding. Direct3D 11, Direct3D 12 and Vulkan programs now see that the adapter left the
  system, and their waits end with a device-lost error. (BD-179)
- **Windows Terminal no longer loses its Direct3D 11 device after it starts.** Before, its window could stay empty
  for about 2 s, a few times right after it started. The known issue of tester.35 is gone. The notification centre
  (Win+N) also no longer loses a Direct3D 11 device when it starts. (BD-198, BD-283)
- **llama.cpp on HIP at the 12 GiB carve-out: no `hipErrorUnknown` at the first prompt.** When a kernel's code
  cannot get system memory, the runtime now puts it in graphics memory. The known issue of tester.35 is gone.
  (BD-277)
- **Monitors with a short vertical blank, for example the LG FHD monitor at 100 Hz.** The driver refused the
  preferred mode of this monitor, 1920x1080 at 100 Hz, because its vertical blank is only 20 lines. The driver now
  accepts a short vertical blank, as the Linux driver does. We did not have this monitor connected for the final
  test of this release: if you have one, please tell us if the 100 Hz mode works. (BD-177)
- **Direct3D 12 ray tracing with deferred collections.** A ray tracing state object that a program built from a
  collection, and then built again from that state object, could use shader data that was already released. The
  data now stays for as long as the state object uses it. (BD-231)
- **Direct3D 12 mesh shaders of older shader compilers.** A mesh shader whose output repeats one element on one
  register, as an older dxc writes for `out vertices float4 v[4] : SV_POSITION`, was refused, and the program could
  crash. (BD-286)
- **Direct3D 12 ExecuteIndirect with mesh shaders and root arguments.** A command signature that changes root
  constants or root descriptors together with a mesh dispatch was refused with `E_OUTOFMEMORY`. (BD-288)
- **Vulkan: a buffer update at an offset no longer stops the GPU.** A valid `vkCmdUpdateBuffer` of 65536 bytes at a
  small offset could read past the end of its data and cause a GPU timeout. This is fixed for 64-bit and 32-bit
  programs. (BD-287)
- **Vulkan memory budget.** The Vulkan driver for 64-bit programs reported a used memory of 0 and a fixed budget.
  It now reports the memory that is in use, so programs such as llama.cpp on Vulkan can size their memory pools
  to the free memory. (BD-202)
- **Vulkan: buffer memory that cannot be exported.** The Vulkan driver said that it could export buffer memory as
  a Win32 handle, but the export always failed. It now says that this memory cannot be exported. (BD-203)
- **Vulkan: presents through GDI no longer block the program.** When a 64-bit Vulkan program presents through GDI
  (the fallback route), a worker thread now does the copy to the window. Before, the program waited for each frame
  on its own thread, and the GPU did no work for about a quarter of each frame. 32-bit programs keep the old
  behaviour in this release. (BD-206)
- **OpenGL: no crash when a program ends.** The OpenGL driver could crash with `0xC0000005` when an OpenGL program
  ended, after all its work had passed. (BD-238)
- **Direct2D on the per-application DXVK files.** When DXVK's `d3d11.dll` is next to a program, Direct2D could not
  make its device (`E_INVALIDARG`). The installed route was not affected. (BD-241)
- **Settings > Display no longer makes the desktop composition lose its device.** This is one cause of the black
  screens of GitHub #40. The report stays open for its other causes. (BD-168)
- **Old copies of driver settings after an update.** An update from tester.30 or earlier left old copies of the
  driver settings in the registry. The setup now moves them to an archive file. (BD-191)

## Known issues

- **D3D12 heaps stay in graphics memory after `Evict` (BD-052).** When a D3D12 game evicts a heap or makes it
  with `D3D12_HEAP_FLAG_CREATE_NOT_RESIDENT`, the heap still uses graphics memory. The driver keeps imported heaps
  resident, as tester.35 did. A fix for this was ready, but it caused a GPU hang at the start of 3DMark. We removed
  it from this version. A different fix comes in a later version.
- **llama.cpp on HIP generates tokens more slowly than llama.cpp on Vulkan (BD-132).** The llama.cpp that the setup
  offers uses HIP. It processes prompts quickly, but it generates tokens about 1.4 times more slowly than llama.cpp
  with its Vulkan backend on this driver. For the fastest token generation, use the official Windows Vulkan build
  of llama.cpp (`llama-<version>-bin-win-vulkan-x64.zip` from github.com/ggml-org/llama.cpp). It runs on this driver
  with no extra steps. Programs that let you select the backend, for example LM Studio, can also use Vulkan. We
  continue to make HIP faster.
- **A restart can stop at a black screen.** On the BC-250, a restart can stop after Windows has shut down: the
  screen stays black and Windows does not start again. On our test unit this occurred in about 1 of 20 restarts,
  with every driver version that we tested. It also occurred twice when our driver did not run (once after we
  removed it, and once when it did not start). Windows has completed its shutdown when this occurs, so no data is
  lost. If the screen stays black for more than 5 minutes after a restart, switch off the PC at the wall or at the
  power supply switch. Wait 10 seconds and switch it on again. The PC then starts normally, and the driver starts
  as usual. The setup can ask for restarts. If this occurs during the setup, do the same, and the setup continues
  at the next start. The cause is not known yet. (BD-145)
- **Games with module checks while test signing is on.** This tester package is test-signed, so Windows runs in
  test mode. Games that check the signatures of the modules that they load, or that use a kernel anti-cheat, can
  refuse the user-mode files of the driver in this mode. Counter-Strike 2 does this check. This ends when Microsoft
  signs the driver package and test mode is off. (BD-160)
- **Please report blank Explorer bars.** A tester reported on tester.35 that the top of each Explorer window (the
  title bar, the address bar and the command bar) was blank. This release has fixes for related drawing faults,
  but this case never occurred on our test unit. If parts of Explorer windows, the taskbar or Start stay blank on
  tester.36, please report it with the time when it occurred. (BD-282)
- **Update from tester.31 or tester.31v2 on Windows 11 24H2 or later:** until the update is complete, the old driver
  is still installed, and Windows Security can make the desktop flicker. The Smart App Control button of the setup
  window opens Windows Security. Before you start the setup, open PowerShell as administrator and run:

  ```powershell
  $k='HKLM:\SOFTWARE\amdgpu-wddm\AppRouter'; if (!(Test-Path $k)) { New-Item $k -Force | Out-Null }; $d=@((Get-ItemProperty $k -ErrorAction SilentlyContinue).Deny) + 'sechealthui.exe' | ? { $_ } | Select-Object -Unique; New-ItemProperty $k -Name Deny -PropertyType MultiString -Value $d -Force | Out-Null
  ```

  This adds Windows Security (`sechealthui.exe`) to the list of applications that always draw on the processor. It
  keeps the entries that are already in the list. It has an effect immediately, without a restart. An update from
  tester.31v3, tester.32, tester.33, tester.34 or tester.35 does not need it.
- **Counter-Strike 2 sometimes stops drawing new frames** with no error, while the game still runs. On our BC-250 this
  occurred in 4 of 24 runs of the bots demo. Close the game and start it again.
- A passive adapter that does not identify itself works only when it is connected at the start of Windows.
- Do not use hibernation: the first resume can crash Windows with `0x116`. Set the power button to "Shut down".
- **Some Direct3D 12 games stop for up to one second** while they compile shaders, also in places you visited
  before. Clair Obscur: Expedition 33 does this. We work on it.
- **This release does not offer Ollama.** An Ollama that you installed with an earlier release stays installed.
- **A hang of the compute queue that the driver cannot stop** still stops Windows with `0x116`, as for a hang of the
  graphics queue.
- **A pixel shader that writes to memory at 8 or 16 samples** can also write for pixels at the edge of a triangle
  that the triangle does not cover. At 1 and 4 samples, and at sample frequency, it does not. Earlier releases also
  have this problem.
- **Direct3D 12 ignores ForcedSampleCount when a render target or a depth buffer is bound.** Earlier releases also have
  this problem.
- **Vulkan: the query counters of geometry shader primitives and of generated primitives read 0** on this graphics
  chip. The other pipeline statistics have their values.
- **Direct3D 12 stream output:** when a program draws a geometry shader stream 1, 2 or 3 and all its streams
  together need more than 8 clip and cull distances, that stream gets no clip or cull distance.
- **Indirect draws: the driver reports at most 4096 draws in one indirect draw call** (Vulkan
  `maxDrawIndirectCount`). The mesh shader path of this chip records each draw on the processor, so a higher limit
  would make each such call record all its draws, whatever its count.
- **When a Direct3D 12 game clears its driver cache**, the shared cache of the Vulkan driver
  (`%LOCALAPPDATA%\mesa_shader_cache`) stays. To clear it, remove that folder while no game runs.
- **32-bit Vulkan games:** VSync off stops only the wait for the desktop composition, because their picture goes
  through GDI, which cannot tear. The maximum frame latency has no effect there, because such a game can never
  queue more than one frame.
- **Game profiles: the driver reads only the options of each format that this route can use.** DXVK options of
  DXVK's own swap chain and of the adapter identity (for example `dxgi.customVendorId`, `dxgi.maxDeviceMemory`,
  `dxgi.enableHDR`) have no effect, because Windows' own DXGI does that work. A program name in a file must be
  exact, with the same upper and lower case letters. vkd3d-proton cannot name a program file whose name has
  letters outside ASCII.
- **A tool that reads AMD's identity data, for example a monitoring tool, can report the revision of a Radeon RX 6700
  series chip** instead of the revision of the BC-250. That is the identity that lets FSR 4 start. It does not change
  the graphics chip, its clocks or the driver. For a Direct3D 12 program, set "Allow FSR 4 in games that include it"
  to off for that program, and the program sees the revision of the BC-250.
- AMD's frame generation does not change: only the upscaler uses the new identity.
- **PyTorch venvs after a driver update:** a venv keeps the DLLs of the earlier version until you run the attach
  step for it again. `-Check` then says that an earlier payload is attached.

## Settings affected

- The installation keeps the settings that you changed. The settings list of the driver has new entries in this
  release, and the setup moves your values to the new list.
- The defaults do not change: 24 graphics cores (`CuMode`), a graphics clock limit of 2000 MHz (`DpmMaxMHz`) and
  large VRAM pages on (`LargePages` 1).
- New settings of the two temperature rules (BD-281). Set them with `bc250kmd_cli state set <name> <value>`.
  The driver reads them when it starts. 0 turns a rule off, and the driver uses the default for a value that it
  refuses.
  - `DpmThermalRate`: the temperature rise for the first rule, in thousandths of a degree C a second. Default
    1500.
  - `DpmThermalRateFromMc`: the temperature from which the first rule acts, in thousandths of a degree C. Default
    80000.
  - `DpmThermalHighZoneMc`: the temperature from which the second rule acts, in thousandths of a degree C. Default
    80000.
  - `DpmThermalHighZoneMHz`: the highest graphics clock of the second rule. Default 1800.
- New setting `FanRiseConfirm` (0 or 1, default 0): with 1, the fan boost needs two temperature rises one after the
  other. The driver reads it when it starts.
- The setup moves old copies of driver values under `HKLM\SYSTEM\CurrentControlSet\Services\bc250kmd\Parameters`
  to `%ProgramData%\amdgpu-wddm\installer\legacy-parameters-<time>.json`. It reads the archive back and compares
  it before it removes a value. (BD-191)
- The driver writes the `HardwareInformation` values (`AdapterString`, `ChipType`, `DacType`, `BiosString`,
  `MemorySize`, `qwMemorySize`) into its driver key when it starts. (BD-245)
- The attach step of PyTorch lists each venv that it changes in `%ProgramData%\amdgpu-wddm\rocm-venvs`. The
  uninstaller puts AMD's DLLs back into each listed venv and then removes the list. A venv that no longer exists is
  skipped with a line in the uninstall log. If a Python of a listed venv is open during the uninstall, that venv
  keeps our DLLs: the uninstaller gives a warning with the venv's folder, and `pip install --force-reinstall
  rocm-sdk-core rocm-sdk-libraries` in that venv puts AMD's DLLs back.

## Tested

Host tests on the build computer, with no GPU, on the files of this release:

- Every component build of this release passed its host tests, with 0 failures: the Direct3D 11 engine tests (243
  cases) and the Direct3D 12 engine tests (222 cases), each for 64-bit and 32-bit programs, the tests of the
  per-game options, the shader cache size limit, the shader cache policy and the compile admission, the Vulkan
  queue, submission and buffer lifetime tests of the Vulkan drivers (3123 test conditions), and the tests of
  the PyTorch attach step.

Tests on a BC-250 with Windows 11:

- An earlier build of this release, with the same setup, kernel driver and Nagi Control App files (only its Vulkan
  drivers were different), passed every step of our installer test: an update over tester.35 that kept a changed
  graphics clock limit, an uninstall and a new install that kept the settings, an install from the command line
  with no questions answered, the confirmation of the first start, and a check that this release driver refuses
  the raw register requests of the lab driver.
- This release was installed after an uninstall. The driver started after the restart, the start confirmation
  task ended without an error, and the desktop used the graphics chip. In the time of the tests below, Windows recorded no GPU timeout and no
  stop.
- Quake II RTX ran its time demo with ray tracing pipelines (73.7 frames a second) and with ray queries (73.9 frames
  a second) at 1280x720. With tester.35 it got 72.8 to 73.5 frames a second. An earlier build of this release got
  only 63 to 65 frames a second: its Vulkan driver held each submission until the earlier GPU work was complete.
  This release does not have that change.
- Rise of the Tomb Raider (Direct3D 12) ran its built-in benchmark to the end at the default graphics clock limit of
  2000 MHz: 63.13 frames a second overall (Mountain Peak 81.22, Syria 52.75, Geothermal Valley 53.70). The highest
  temperature was 87.9 C, and our test rule did not stop the game. The new temperature rules lower the clock in the
  hot scenes, so the score is lower than with tester.35 at 1800 MHz (90.73).
- The Witcher 3 Remaster (Direct3D 12) with ray tracing on and the high preset loaded a saved game, and Geralt
  walked in the world for about 2 minutes with no fault in the picture. The highest temperature was 84.8 C.
