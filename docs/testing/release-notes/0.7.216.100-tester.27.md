# amdgpu-wddm 0.7.216.100-tester.27

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and amdgpu-wddm Control of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes a record that
only this installer and this control program read.

The release before this one is 0.7.216.100-tester.26. This release replaces it. The notes of 0.7.216.100-tester.26
list the changes since 0.7.216.100-tester.25, and they apply to this release too, with the changes below.

## New

- **amdgpu-wddm Control shows the GPU memory size of the BC-250.** The board keeps a part of the machine's
  memory for the GPU. The Performance page of amdgpu-wddm Control now has a Board memory card, which shows the
  size that is in use now. The card is made to change that size too, with two choices, 8 GB and 12 GB, but on
  this build it says that a change is not available (BD-116). Read the first known issue below.
- **Only a BC-250 gets the size control.** On another adapter the Board memory card shows the memory size and
  says that the control is not supported. The driver touches no board hardware there.
- **The automatic clock control may now go up to 2000 MHz.** The release before this one let it go up to
  1500 MHz. The GPU still starts at 1000 MHz, it still drops to 500 MHz when nothing uses it, and the
  temperature and voltage limits are the same as before. You can still choose a lower limit in the Tuner page
  of amdgpu-wddm Control. A machine that locks up under load at a high clock speed is a known risk of this
  hardware: choose a lower limit if that happens, and tell us.
- **The kernel-mode driver keeps a record of each HIP dispatch.** Before a HIP program sends work to the GPU,
  our HIP runtime gives the driver the name of the GPU function and the place of the work in the queue. If the
  GPU then faults or stops, the driver's record names the function that caused it. This is how we found the
  HIP fault below.
- The kernel-mode driver is version 0.7.216.28.
- The 64-bit Vulkan driver, amdgpu-wddm Control, its helper library, `bc250kmd_cli` and the HIP runtime are new
  builds.

## Fixed

- **A Vulkan program now sees the real GPU memory size.** The 64-bit Vulkan driver reported the memory size of
  the machine the driver was first measured on, which was 8 GB, whatever the board was set to. It now reports
  the size the board really keeps for the GPU, so a program that asks how much GPU memory it may use gets a
  larger answer after you choose 12 GB. A program that needs more memory than 8 GB can now be told that the
  memory is there.
- **A Vulkan program that gives one of its GPU locks to another program keeps its own copy.** Vulkan lets a
  program hand one of its GPU locks to another program through a Windows handle. The 64-bit Vulkan driver took
  the handle away from the program that gave it, so that program then held nothing. It now keeps its own copy,
  as Vulkan asks, and it applies the rights, the inheritance and the name that the program asked for. The other
  program cannot use the lock yet: read the known issues.
- **A HIP program no longer makes the GPU fault (BD-110).** Our HIP header gave `gridDim` as a count of
  work-items, not as a count of workgroups. A GPU function that steps through its data by the size of the grid
  then went far past the end of its buffer, the GPU faulted, and Windows stopped with stop code 0x116. The
  driver's dispatch record named the function. Now the header gives the count of workgroups, and the HIP
  runtime, `vadd.exe` and `bc250hipblas.dll` are built again with it. The same change fixes other device
  functions of the header, for example atomic operations, the ballot of a part of a wave and conversions of
  half-precision numbers.

## Measured on our test board

These are results from the test of this release on our own BC-250, with the GPU memory size at 8 GB and the
automatic clock control on. Your results can be different.

| Program | Mode | Result |
| --- | --- | --- |
| Rise of the Tomb Raider, benchmark | Direct3D 12, preset High, empty shader cache | 51.24 frames per second overall |
| Rise of the Tomb Raider, benchmark | Direct3D 12, preset High, shader cache of an earlier run | 77.59 frames per second overall |
| Quake II RTX, timedemo | ray tracing with `VK_KHR_ray_tracing_pipeline` | 59.73 frames per second |
| Quake II RTX, timedemo | ray tracing with `VK_KHR_ray_query` | 60.92 frames per second |
| The Witcher 3 Remaster, in the game world | Direct3D 12, preset High with ray tracing | 13.0 frames per second |

| llama.cpp, TinyLlama 1.1B Q4_0 | HIP, generation of 128 tokens (tg128) | 122.31 tokens per second |

On HIP, the greedy answer of TinyLlama, 16 tokens, was the same as the answer of the processor.

## Experimental: HIP runtime

- This package has our own HIP runtime, `amdhip64.dll`, with our hipBLAS library `bc250hipblas.dll`. The
  installer puts them in the `tools\hip` folder of the install folder and adds that folder to the end of the
  system PATH, so a HIP program finds them after the restart that ends the installation. If AMD's own
  `amdhip64.dll` is in `System32` or earlier on PATH, Windows loads that one first. The uninstaller deletes
  the folder from PATH again.
- To check the runtime, run `tools\hip\vadd.exe`. It adds two vectors on the GPU and compares each value with
  the result of the processor. It must report a pass.
- This package does not contain llama.cpp. The source repository has the recipe that builds the HIP backend of
  llama.cpp for this runtime, in `compute/hip/patches`. The recipe builds llama.cpp with flash attention on, and
  it keeps each model buffer below the Windows limit in the known issues (BD-117). TinyLlama 1.1B and the dense
  Gemma 4 12B model load and answer on HIP with it.
- We compared the output of the whole TinyLlama model on HIP, with flash attention on, with CUDA on an RTX 4090.
  The mean KL divergence was 0.003, so the two give almost the same results.

## Known issues

- **The Board memory card cannot change the GPU memory size on this build (BD-116).** Before the driver offers
  a change, it checks its route to the board's settings memory. On our test board that check fails, so the card
  offers no size, writes nothing and says that a change is not available. The board keeps the size that it has.
  The fix comes in the next release. Until then, only Linux can change the size.
- **A Vulkan program cannot yet use a GPU lock that it gets from another program (BD-105).** The program that
  gets the Windows handle of a lock receives `VK_ERROR_INVALID_EXTERNAL_HANDLE` when it opens the handle, and
  also when it opens the lock by its name. The lock stays usable in the program that gave it. Two programs that
  share their GPU work through such a lock do not work together on this release.
- **A HIP program cannot get one GPU memory block of more than about 4 GiB (BD-117).** On this driver, Windows
  refuses one GPU allocation of more than 0xFFFF0000 bytes, and `CreateAllocation2` returns C000000D. The
  llama.cpp recipe in `compute/hip/patches` therefore limits one buffer to 0xFFFC0000 bytes. llama.cpp then puts
  the model weights in more than one buffer, and a dense model of 12 billion parameters (Gemma 4 12B) loads and
  answers on HIP. A program that asks HIP for one block of more than about 4 GiB still gets the error.
- **Windows gets less memory when the GPU gets more.** At 12 GB the GPU keeps four more gigabytes, and Windows
  has that much less. On a 16 GB board Windows is left with about 4 GB, which is enough for the desktop and a
  language model, and not enough for comfortable work. Choose 12 GB for a program that needs the GPU memory, and
  8 GB for everything else.
- **The real GPU memory size is reported by the 64-bit Vulkan driver only.** The 32-bit Vulkan driver of this
  release is the same build as in 0.7.216.100-tester.26, and it still reports the old measured size. The same is
  true of the shared-lock fix above.
- **Windows itself reports the GPU memory as before.** The size that the Task Manager and a Direct3D program
  read comes from Windows, not from this part of the driver, and it counts memory that no program can use for
  its own data. A number there that is larger than the Vulkan number is not a fault.
- The 64-bit Vulkan driver of this release is a new build, so the shader cache it wrote for an earlier release
  is not read any more. The first start of a Vulkan game takes longer than it did, once.
- The catalog file of the kernel driver (`bc250kmd.cat`) is still different in every build, because every build
  signs a new one. The driver image is the same in every build.
- After a stop with code 0x116 the driver's automatic clock control is left switched off. Check the Tuner page
  of amdgpu-wddm Control after such a stop.
- A program that the router sends to the processor path gets Direct3D feature level 10_0 only. With the release
  setting gpu-default this affects programs whose image the router cannot resolve. Keep the router at gpu-default
  (issue #24).
- Without administrator rights, `bc250kmd_cli clock read` gives no clock and no temperature. Use
  `bc250kmd_cli dpm` in its place (issue #7).
- The desktop compositor composes a full-screen game again while another window covers part of it, for example a
  notification. The driver has no overlay path for such a window yet.
- A screenshot or a screen recording of a full-screen Direct3D 12 game can be black. The game puts its own
  picture on the screen, and the compositor does not get the frames. To record such a game, set
  `AMDGPU_WDDM_D3D12_EXPERIMENT=scanout-flip-off` for it.
- The known issues of 0.7.216.100-tester.26 apply.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.
- **The GPU memory size is not a Windows setting.** It is kept in the board's own settings memory, and no
  installation and no uninstallation of this package changes it. If you choose 12 GB and then go back to
  0.7.216.100-tester.26, the board stays at 12 GB.
- This build writes nothing to the board's settings memory, because the Board memory card cannot change the
  size (BD-116).
- **The highest automatic clock speed, `DpmMaxMHz`, is 2000 MHz in this release.** It was 1500 MHz in
  0.7.216.100-tester.26. The installation changes a stored 1500 MHz to 2000 MHz, and it keeps every other
  stored limit. An earlier release did not record whether 1500 MHz was its own default or your choice, so if
  you chose 1500 MHz yourself, choose it again in the Tuner page of amdgpu-wddm Control after the
  installation. A limit that the installation is given on its command line wins over this change.
- **The system PATH gets one new entry, `<install folder>\tools\hip`, at its end.** The installation adds it
  once, and the uninstaller deletes that entry and no other.
- The driver's private limit for one piece of GPU work is `SubmitWatchdogMs`, the fan's full speed under heavy
  load is `FanLoadBoost`, and both stay as 0.7.216.100-tester.26 set them.
- `EnableDpAudioContainerId`, `EnableRingVmFlush`, `TdrDelay` and the shader cache of the 64-bit Vulkan driver
  stay as 0.7.216.100-tester.26 set them. `TdrDelay` is 10 seconds, written by the installation, and the
  uninstaller puts your earlier value back.
- The graphics settings are `REG_DWORD` values under `HKLM\SOFTWARE\amdgpu-wddm\Graphics` for all games and under
  `HKLM\SOFTWARE\amdgpu-wddm\Graphics\Applications\<program file name>` for one game. No value is set after the
  installation, so each game keeps its own settings until you change one.
- The AMD-format driver version on the Graphics page stays off after the installation, and no installation of
  this package writes it. Windows asks a driver not to change that number after it is installed, and changing it
  can stop Windows Update from working properly on the adapter. Turn it on only for a game that refuses to
  start with the real number, and turn it off again afterwards.

## If something goes wrong

- The Board memory card of this build says that it cannot change the size (BD-116). Do not try to force it. If
  the card shows a size that is not the size of your board, send us the support report.
- If a Vulkan program reports a GPU memory size that does not match the size you chose, send us the support
  report and the program's own report of its memory.
- If Windows stops with stop code 0x116 while a language model or another long GPU job runs, send us the support
  report with the exact command you ran, the model and its batch size. Then check the Tuner page of amdgpu-wddm
  Control, because the automatic clock control is left switched off after such a stop.
- If a Vulkan program hangs for about two minutes and then says that the graphics device was lost, send us the
  support report and say what the program was doing.
- If the fan is too loud, turn off "Full fan speed under heavy load" in the Case fan card of the Performance
  page and restart Windows. Then tell us what the machine was doing.
- If a recording made with the BC-250 encoder looks wrong, send us the recording and say whether
  `BC250_MFT_DEBLOCK` was set for the recording program.
- If the sound device of your monitor disappears or stops after this release, set `EnableDpAudioContainerId` to 0
  and restart Windows. Then tell us what happened.
- If a Vulkan game starts badly or draws wrongly, delete `%LOCALAPPDATA%\mesa_shader_cache` and start it again. If
  that helps, set `MESA_SHADER_CACHE_DISABLE=true` for the game and tell us.
- If `tools\hip\vadd.exe` reports a fail, send us its output and the support report.
- If Quake II RTX or another ray tracing program loses its graphics device, send us the support report with the
  name of the program and the mode you ran.
- If a game has a black screen or a wrong picture in full screen, set
  `AMDGPU_WDDM_D3D12_EXPERIMENT=scanout-flip-off` for that game and start it again. Then tell us what happened.
- If a game fails after you change a graphics setting, set the setting back to "Application decides" on the page
  where you changed it.
- Send us the support report from amdgpu-wddm Control. It holds the driver log and the stored graphics settings.
