# amdgpu-wddm 0.7.207.100-tester.12

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

## New

- The kernel-mode driver is version 0.7.207.1.
- A game can now put its own image on the screen directly. The desktop compositor does not copy the image first. The
  driver accepts the image of the game for the display hardware when the image has the size, the layout and the colour
  format of the current screen mode, and when the image is in graphics memory. The driver refuses every other image,
  and the screen keeps the image it has. The driver counts each refusal and writes the reason in the driver log, so a
  support report says why a game did not get the direct path. Only a game that asks for the direct path gets it. The
  Direct3D 12 driver asks for it only when you turn on the experiment `scanout-flip-1920x1200` for that game, so a
  normal game behaves as it did before. The Direct3D 11 driver does not ask for it yet.
- When the GPU has no work for 3 seconds, the driver sets the GPU clock to 500 MHz. The voltage stays the same as at
  1000 MHz. The clock returns to 1000 MHz or more at the first work the GPU gets. The driver needs one measurement
  period and one clock change for this, which is some 25 to 35 milliseconds. A game or an application therefore starts
  at the normal clock. Work on the graphics engine and work on the copy engine both count. A desktop that repaints a
  window now and then keeps the idle clock. The driver does not use the idle clock while a temperature limit, a
  measurement tool or a clock floor holds the clock. It does not use the idle clock at all in the fixed-clock mode. If
  the GPU does not accept 500 MHz, the driver tries 800 MHz, and then stays at 1000 MHz.
- The package installs an H.264 video encoder that runs on the GPU. Windows calls it a Media Foundation transform. A
  program that records the screen or a camera can now make H.264 video with the GPU of the BC-250. Game Bar, the
  Camera application and a Chromium browser find the encoder themselves. The installer puts
  `amdgpu_wddm_mft_h264.dll` in the `mft` folder of the install folder. Then it writes the registry keys that Windows
  needs to find the encoder. The uninstaller removes those keys and that file. A later installation of a release without the encoder also
  removes them.
- The graphics libraries for Direct3D 11, Direct3D 12 and Vulkan carry the newest code of the projects they come from
  (DXVK, vkd3d-proton with dxil-spirv, and Mesa RADV). `THIRD-PARTY.md` names the exact commit of each library.

## Fixed

- Task Manager and other applications that use DirectComposition lost their graphics device and had to build a new
  one. The driver refused the one-byte-per-pixel image that such an application shares with the desktop compositor,
  and it now accepts it. This was most visible as the graphs of Task Manager.
- The driver gave a row size for a display format that it does not offer as a screen mode. No application saw this,
  because the display code asks for the format first. The two answers now agree.

## Known issues

- We did not test an application with the H.264 encoder on the BC-250 before this release. We tested the encoder
  itself, with our own test program.
- The encoder tells Windows two things: that it is a hardware encoder, and that it gives its frames back
  asynchronously. Windows can therefore give the encoder to a program that asks for any asynchronous encoder. It does
  not give it only to a program that asks for a hardware encoder. If a program records worse video than before, or
  does not record at all, send us the support report. We can make a release that does not install the encoder.
- If you install 0.7.205.100-tester.11 over this release, the registry keys of the encoder stay. Only the uninstaller,
  or a later release without the encoder, removes them.
- The direct screen path is for a game in fullscreen or borderless mode. The desktop compositor decides for a
  borderless window, so the path is not sure there.
- After a crash or a power loss the driver closes the GPU desktop path, and the CPU draws the desktop (slower
  animations). "Reopen the GPU desktop path" on the Recovery page of amdgpu-wddm Control opens it again.
- Some applications that use WinUI or XAML do not draw their window content on the GPU. Windows apps are not affected,
  because they use the CPU.
- 32-bit Direct3D 12 applications do not have a driver yet.
- Secure Boot must be off, and Windows runs in test mode, because we sign the driver with a test certificate. The
  desktop then has the words "Test Mode" in its corner.
- The installation needs internet access for the AMD GPU firmware, or a folder with the firmware files
  (`INSTALL.md`, section "GPU firmware").
- The Microsoft Visual C++ 2015-2022 Redistributable (x64) must be installed.
- After each logon, a small blue window confirms the driver start for about one minute. Do not close it.

## Settings affected

- The installation keeps the settings you changed. A setting that you did not change gets the new default of this
  release.
- The installer lists each setting it changes before it changes anything.
- This release adds two driver settings, and the installer writes both of them. An administrator can change either
  value under the `Parameters` key of the driver and then restart the computer. Set `EnableScanoutAdmit` to 0 to refuse
  the direct screen path for every game. Set `DpmIdleMHz` to 0 to keep the GPU clock at 1000 MHz or more at all times.
  With both values at 0, the driver behaves as version 0.7.205.1 did.
- The H.264 encoder has no setting in the control application. Each release decides if the installer writes the
  registry keys of the encoder.
