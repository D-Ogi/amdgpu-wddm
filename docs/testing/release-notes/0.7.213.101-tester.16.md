# amdgpu-wddm 0.7.213.101-tester.16

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and amdgpu-wddm Control of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes a record that
only this installer and this control program read.

The release before this one that we gave to a tester is 0.7.208.100-tester.13. We built 0.7.212.100-tester.14 and
0.7.213.100-tester.15 and gave them to nobody, so everything that those release notes described is new to you here as
well. This release is tester.15 with one fix of the desktop driver, the first item under "Fixed".

## New

- The kernel-mode driver is version 0.7.213.1. The numbers 0.7.209 to 0.7.212 name the same work while we wrote it in
  parts. We released no driver with those numbers.
- Every finished change of this release is on when you install it. Each one also has one setting that takes it away
  again, for the case where a change makes your machine worse: write 0 into that setting, restart Windows, and that
  one change is gone while the rest stay. The list is under "Settings affected".
- The driver reads the board's own fan controller: the fan speed in revolutions per minute, the fan power in percent,
  and the temperature that the board measures on the processor. The driver only reads. It never sets the fan speed,
  and it writes no setting of that chip, so the board keeps its fan curve and the BIOS "Fan Setting" option works as
  before. If the chip does not answer the way this board's chip answers, the driver stops reading it and says so.
- The reading is on from this release. Another monitoring program can read the same hardware at the same time, and
  both readings then become wrong. Close HWiNFO, Open Hardware Monitor, AIDA64, MSI Afterburner or a similar tool
  before you trust a fan value. If you would rather have no port access at all, write 0 into `EnableHwmon` and
  restart Windows.
- amdgpu-wddm Control shows the fan values. The support report carries the same values. The report says `no reading`
  and the reason when the reading is off, when the fan controller did not answer, or when the newest value is too old.
- The driver lowers the GPU clock earlier when the chip gets hot. Until this release the first rule that read the
  temperature acted at 87 C, which is also where our own test runner ends a game. The driver now starts stepping the
  clock down a little below that, and it looks at how fast the temperature is still climbing, so it meets the limit
  with a small step instead of a large one. In our replay of 21 recorded game sessions the old rules held 87 C for
  16 seconds and the new ones peaked at 86.5 C with no stop at all.
- The driver can tell the desktop compositor that it accepts a game's own picture buffer on the screen, and the
  desktop driver can now be asked that question. This is the next step of the work that lets a fullscreen game put its
  own frames on the screen without the desktop composing them. In this release the desktop driver always answers no
  and writes down the reason, so you will see no change on your screen from this step.
- Two driver requests cost less than before. The small blue window that confirms the driver start after each logon,
  and the "keep this setting" step of the lab tuning tools, no longer ask Windows to idle the GPU while they run.
  Before this release each of those requests stopped graphics work for a moment.
- The H.264 video encoder is faster. It holds two pictures at the same time. It filters a whole picture in one
  dispatch. It reads the quantiser that the content needs. A client that asks for low latency still gets one picture
  at a time, because the second picture costs it one frame of delay.
- A recording with a fixed quantiser gives the same bytes as before, to the byte. A recording that asks for a bit rate
  can change its byte count by up to 3 %.
- The support report holds more counts. Four lines say what the driver saw on the direct screen path: the kind of
  description that each surface arrived with, what the system asked for at each change of the picture on the screen,
  how many pictures went through the desktop, and whether this start accepts a game's own picture buffer. More lines
  count the gap between the GPU work queue and the screen refresh, whether each finished packet and its notification
  arrived together, and what the new temperature rule did. These counts are instruments. They change no behaviour.
- A picture buffer whose creator asks to put it on the screen directly now starts on a 4 KiB boundary. The screen
  hardware can only read a buffer that starts on such a boundary. No other buffer changes.
- A lab operator can give the automatic clock a voltage curve of their own, and can set a clock limit, an undervolt
  and a temperature cap for the processor. Each one runs as a trial that the driver takes back by itself if the
  machine does not stay healthy. These are off until an operator sets them, because they are values a person
  chooses, not features.

## Fixed

- With the Direct3D 11.1 front of the desktop driver on, the desktop could stop between the logon screen and the
  desktop: the wallpaper and the icons showed, the Start menu did not, and the logon screen stayed partly visible. The
  desktop driver did not know one optional part of a shader that Windows sends through that front, and stopped in a
  self-test that showed an invisible message box inside the desktop compositor. The desktop driver now reads past
  that part. If such a self-test fails again, the compositor stops and Windows starts it again, instead of a frozen
  desktop.
- A Direct3D 12 program that asked for a texture to share with another process got a refusal. The driver now makes
  that texture, inside a known shape: a 2D texture, one mip level, one slice, one sample, a size up to 8192 in each
  direction, a GPU-only heap, and one of the admitted formats. A program that never asks for a shared texture sees no
  change, because the driver asks a second time only inside that shape. The release before this one refused the
  texture and kept the device alive.
- A Direct3D 12 program lost its graphics device the first time that the system asked a command queue to wait for a
  fence. The driver now accepts that question and answers it. The system does the waiting itself, as it did for a
  signal, and the driver performs no fence operation of its own.
- amdgpu-wddm Control no longer reads the driver log with a request that stops graphics work every few seconds while
  its graphics page is open. That request cost about 300 milliseconds each time, which a game could feel.
- An install over an older release left the files of that release in the install folder, and it left the driver package
  of that release in the Windows driver store. Each install added one more package. The installer now removes the files
  that the older release installed and this release does not install. It also removes our older driver packages. It
  keeps the package that the GPU uses now, and the package of the release before this one, because that one is the way
  back. It removes only a file that still holds the bytes of that older install. A file that somebody changed stays,
  and the installer gives its name.

## Known issues

- Nothing of the direct screen path is measured on this board. The driver and the desktop driver now both carry it,
  and Windows asks the question, but the desktop driver of this release always answers no. It writes the answer and
  the reason for it into the log, which is what the path is for in this release. No run has shown a game's own buffer
  on the screen, and this release cannot show one.
- The new temperature rule is measured against recorded sessions, not against a new game session on your machine.
- A wait on a fence that a second process opened is not measured. The driver accepts such a wait, and no test run has
  reached one yet. The driver writes a log line at the first wait of each kind in a program, so a support report says
  whether a run reached one.
- A shared texture outside the known shape above still gets a refusal.
- The Vulkan driver for 64-bit Vulkan programs is the build of 2026-09-27, as in the four releases before this one.
  It copies each frame through the processor, and it has no shader disk cache. 32-bit Vulkan programs get the newer
  build. Direct3D 11 and Direct3D 12 programs are not affected: they get the newer build.
- The Direct3D 11 driver, the Direct3D 12 driver and the desktop router of this release are new builds. If a game
  does not start, or draws wrong, send us the support report. The release before this one is the way back.
- We did not test a program with the H.264 encoder on the BC-250. We tested the encoder itself with our own test
  programs, for BGRA input and for NV12 input.
- The encoder tells Windows two things: that it is a hardware encoder, and that it gives its frames back
  asynchronously. Windows can therefore give the encoder to a program that asks for any asynchronous encoder. It does
  not give it only to a program that asks for a hardware encoder. If a program records worse video than before, or
  does not record at all, send us the support report. We can make a release that does not install the encoder.
- If you install an older release over this one, the registry keys of the encoder stay. Only the uninstaller, or a
  later release without the encoder, removes them.
- The direct screen path is for a game in fullscreen or borderless mode. The desktop compositor decides for a
  borderless window, so the path is not sure there.
- After a crash or a power loss the driver closes the GPU desktop path, and the processor draws the desktop (slower
  animations). "Reopen the GPU desktop path" on the Recovery page of amdgpu-wddm Control opens it again.
- Some programs that use WinUI or XAML do not draw their window content on the GPU. Windows apps are not affected,
  because they use the processor.
- 32-bit Direct3D 12 programs do not have a driver yet.
- Secure Boot must be off, and Windows runs in test mode, because we sign the driver with a test certificate. The
  desktop then has the words "Test Mode" in its corner.
- The installation needs internet access for the AMD GPU firmware, or a folder with the firmware files
  (`INSTALL.md`, section "GPU firmware").
- The Microsoft Visual C++ 2015-2022 Redistributable (x64) must be installed.
- After each logon, a small blue window confirms the driver start for about one minute. Do not close it.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.
- The installer lists each setting it changes before it changes anything.
- Each change of this release has one setting that takes it away. All five are `REG_DWORD` values, the driver and the
  desktop router read them when they start, and each one needs a restart of Windows:
  - `EnableHwmon` under the driver service's `Parameters` key. 1 (the new default) reads the fan controller. 0 means
    that the driver reads no fan value and touches no port of that chip.
  - `EnableDirectFlipHandshake`, same key. 1 (the new default) tells the desktop driver that this start accepts a
    game's own picture buffer on the screen. 0 says nothing, as the release before this one did.
  - `NotifyDpcInReport`, same key. 1 (the new default) lets the driver tell Windows about a finished packet in the
    same step that reports it. 0 gives the extra step of the release before this one.
  - `DirectFlipFront` under `HKLM\SOFTWARE\amdgpu-wddm\DesktopRouter`. An absent value and 1 (the new default) put
    the Direct3D 11.1 front in the desktop driver, so that Windows can ask the flip question at all. 0, and a value
    of the wrong kind, give the desktop driver of the release before this one.
  - `DpmThermalZone`, the driver service's `Parameters` key again. An absent value and any value other than 0 (the
    new default) run the new temperature rule. 0 runs the rule of the release before this one: the clock first steps
    down at 87 C and never earlier.
- `HwmonBasePort` at 0 (the default) means the built-in address `0x0A20`. The driver admits `0x0A00` and `0x0A10`
  beside it, and it refuses every other value.
- `EnableScanoutAdmit` and `DpmIdleMHz` of the releases before this one keep their meaning and their defaults.
- If you installed the unpublished 0.7.212.100-tester.14, that installer wrote `EnableHwmon` 0, and this installer
  keeps a value you appear to have chosen. Write 1 into it by hand and restart Windows to get the fan reading.
- The kernel driver has more settings for a lab operator. They are `REG_DWORD` values under the driver service's
  `Parameters` key, and each one is absent in this release, which means the operator has chosen nothing. They are
  `HwmonExpectId`, `HwmonDutyProven`, `HotSubmitLog`, `CpuTune`, `CpuLab`, `CpuMaxMHz`, `CpuUvSteps`, `CpuTempC`,
  `CpuTrialMs`, `CoreMask` and `DpmCurve1000` to `DpmCurve2000`. `driver/kmd/README.md` and `docs/hardware.md` hold
  the rules and the limits of each one.
- An administrator can turn one behaviour of the Direct3D 12 driver off for one program. Set the value `Experiment`
  under `HKLM\SOFTWARE\amdgpu-wddm\D3D12\Applications\<program file name>` to one name, or to several names with a
  comma between them. Each name of this kind ends in `-off`. The same value under `HKLM\SOFTWARE\amdgpu-wddm\D3D12`
  turns a behaviour off for every program. This release adds two names. `shared-create-retry-off` gives the refusal
  of the release before this one for a shared texture. `fence-wait-accept-off` loses the device at a queue wait on a
  fence, as the release before this one did. The five names of the release before this one keep their meaning:
  `raytracing-tier-off`, `direct-entry-off`, `deferred-replay-off`, `recording-bind-off` and `retire-handoff-off`.
  The name `replay-log` changes no behaviour: it writes a log of the recording work for a support report.
- Three environment values take one part of the encoder back to its older behaviour. `BC250_MFT_DEPTH=1` holds one
  picture at a time. `BC250_MFT_DEBLOCK=waves` and `BC250_MFT_SERIAL_DEBLOCK` select the two older filter schedules.
  Set them in the environment of the program that records.
- The value `AmdgpuWddmSparseBinding` of the adapter key keeps its meaning and its default.
