# amdgpu-wddm 0.7.216.100-tester.28

A tester release of amdgpu-wddm, an experimental Windows 11 x64 driver for the GPU of the ASRock BC-250. It is for
people who want to test the driver on their own BC-250 and report what happens. It is not ready for daily use.

The kernel-mode driver, the installer and amdgpu-wddm Control of this release belong together. Install the three of
them from this package, and do not mix them with the files of another release. The kernel driver writes a record that
only this installer and this control program read.

The release before this one is 0.7.216.100-tester.27. This release replaces it. The notes of 0.7.216.100-tester.27
list the changes since 0.7.216.100-tester.26, and they apply to this release too, with the changes below.

## How to install

Unpack the zip file to a local folder, then double-click `setup\amdgpu_wddm_setup.exe` in that folder. The setup
window asks for administrator rights itself. It checks the computer, shows what it will change and asks before each
restart of Windows. After each logon it starts by itself and continues. `install.cmd` stays the way to install on the
command line, with all its switches. `INSTALL.md` in the package gives both ways.

## New

- **The setup window is the usual way to install.** It shows the checks, the changes, the consents and the restarts
  in plain words, in English, Polish, Japanese and Korean. On a problem it tells you the next step, and it can
  save a support file. The setup window installs the driver only: for llama.cpp, Ollama or a model, install with
  `install.cmd`.
- **HIP: device-to-host copies of model outputs now run on the GPU.** On our test board, text generation (tg128) is
  about 26 % faster on Gemma 4 12B (39.0 against 30.9 tokens a second) and about 28 % faster on TinyLlama 1.1B.
  Prompt processing is unchanged. `BC250_HIP_GPU_COPY=0` puts the copies back on the processor.
- **amdgpu-wddm Control can change the GPU memory size of the BC-250 (BD-116).** The Board memory card of the
  Performance page offers 8 GB and 12 GB. The change needs an administrator, and it takes effect when Windows
  starts the next time. The card shows the size in use now and the size of the next start apart. "Restore" puts
  back the setting that the board had before the first change. The driver of 0.7.216.100-tester.27 could not
  find the board's settings memory, so its card offered no size. This driver reads and writes it through the
  fixed ports of the board.
- **Direct3D 12 programs can draw one scene into several views with one draw (view instancing, tier 2).** A
  program uses this, for example, for the two eyes of a stereo picture or for the faces of a shadow map. The
  driver reports tier 2 only when its Direct3D 12 engine supports it. It does not report tier 3.
- **Direct3D 12 render passes go to the driver.** The driver now gives Windows its own render pass functions, so
  Windows does not do render passes with its own steps.
- **The Performance page has a new card, "Ray tracing benchmark".** It measures how fast your card traces light and
  shows the result in pictures a second. It needs Quake II RTX on the computer: the free game of NVIDIA, from
  Steam or from the maker's own page. The driver package does not hold the game and never downloads it. The card
  finds a Steam copy by itself, and you can also choose the folder yourself. It says plainly when a folder holds
  no game, no game data, game data it cannot read, or a copy without the test scene.
- One run of the card measures both ways your card can trace light, one after the other, because a game can ask
  for either and the speed differs. The card names them "First way" and "Second way" and gives the technical name
  of each under it. Each way takes about twenty seconds on our own board. The game opens in a small window of its
  own, 1280 by 720, and closes again when it has finished. The card shows the pictures a second, the highest
  temperature and the average clock of each way, with the date and the driver release of the run.
- The test of the card stops by itself when the chip stays at 87 degrees, and after three minutes for each way.
  "Stop the test" ends it at once. The card then says which of those happened instead of showing a number. The
  last ten runs stay on this computer, so you can see whether a new driver release changed the number.
- **amdgpu-wddm Control has a new page, "Windows settings".** It can stop some background activities of Windows,
  for example the diagnostic data service, the indexing service and some telemetry tasks. Each change is optional. The page saves the
  earlier setting before each change, and "Restore" puts that setting back. It does not remove Windows parts, and
  it does not touch security, the network or the Windows Update service. The installer applies the recommended
  changes only when you give it `-ApplySystemTuning`.
- **The installer can install the programs that run language models on the board.** It asks one question for
  each one, and `yes` is the answer in capitals, so Enter is enough. The two are our build of llama.cpp and our
  build of Ollama. Both are open projects under the MIT licence. They go into
  `C:\Program Files\amdgpu-wddm\tools\llama` and `C:\Program Files\amdgpu-wddm\tools\ollama`, and both folders go
  on the machine search path, so you can start them in any command prompt after the restart.
- **The installer can also get a model for you.** After the two questions it shows a short list with the size and
  the licence of each model: Gemma 12B, which is the model this board was measured with, Qwen3 1.7B, which is small
  and quick, and Qwen3.6 35B A3B, which needs the board memory at 12 GB. The answer is none, because a model is a
  download of gigabytes. The model files go into `C:\Users\Public\Documents\amdgpu-wddm\models`. For Ollama the
  installer gets the same model through Ollama itself, which keeps it in its own format in its own folder. A model
  that you choose for both programs is therefore downloaded twice and kept twice, about 13 GB for Gemma 12B. The
  question says so for each model, with the sum, before anything is downloaded.
- **The installer checks an extra and a model before it uses them.** The package holds the address, the size and
  the SHA-256 of every download, and it refuses a file that does not match. A refused, skipped or failed extra
  never stops the driver installation: the driver is installed first, and the extras come last.
- **An installation without a window can choose with switches.** `-Components llama,ollama` and
  `-NoComponents`, `-Models gemma12b` and `-NoModels`, and `-ComponentDir <folder>` to take the files from a folder
  instead of the internet. `prepare-offline.cmd` takes the same switches and puts the files into `components\` and
  `models\` of the prepared folder, next to the firmware.
- **Use `bc250-ollama.cmd` to start our Ollama, not `ollama.exe`.** It is the same program, with the port and the
  model folder of this installation already set. `bc250-ollama.cmd run gemma4:12b-it-qat` in the installed folder
  is the whole of it. A bare `ollama.exe` uses the Ollama defaults, so it can reach another Ollama on the same
  computer instead of ours.
- **Our Ollama can use the board in two ways.** The user environment variable `BC250_OLLAMA_BACKEND` selects
  `auto`, `vulkan` or `rocm_bc250`. The installer writes `auto`, which lets Ollama decide. Stop and start the
  server after a change. An Ollama that you installed yourself is left alone: our copy keeps its models in
  `%LOCALAPPDATA%\bc250-ollama\models` and takes the next free port when the usual one is in use.
- **The uninstaller removes every registration of an extra and keeps your models.** It removes the two folders,
  the two entries in the machine search path, and the logon entry and the settings that an extra wrote.
  `uninstall.cmd -RemoveModels` removes the models as well, from both model folders.
- **The kernel-mode driver saves a record of the GPU programs before it resets a stopped GPU.** The record names
  each wave that was running and its place in the program. `bc250kmd_cli waves saved` shows the record of the
  last reset, and `bc250kmd_cli waves` reads one now.
- **Board controls need a BC-250.** The fan, the clock limits, the processor limits and the memory size are board
  controls. The driver gives them only after it identifies the board as a BC-250. amdgpu-wddm Control and
  `bc250kmd_cli board-caps` read the limits from the driver. On another board the controls say that they are not
  supported, and the driver does not touch the board.
- The kernel-mode driver is version 0.7.216.29.
- The Direct3D 12 driver of both architectures, its engine, the Direct3D 12 and Direct3D 11 GPU drivers of both
  architectures, the 64-bit Vulkan driver, amdgpu-wddm Control, its helper library and `bc250kmd_cli` are new
  builds.

## Fixed

- **A Vulkan program can now use a GPU lock that it gets from another program (BD-105).** The 64-bit Vulkan
  driver opens such a lock by its Windows handle and by its name, with or without `Global\` or `Local\` in the
  name. In 0.7.216.100-tester.27 it gave `VK_ERROR_INVALID_EXTERNAL_HANDLE`.
- **A Direct3D 12 program that builds its states from a pipeline library keeps its graphics device.** The driver
  refused a blend, depth, rasterizer or input layout state that named a pipeline library. Windows then removed the
  graphics device of the program. The driver now accepts a reference to a valid library of the same device.
- **A Direct3D 12 program can now use a GPU lock that the Vulkan driver made (BD-105).** Direct3D 12 reads its
  value, and its waits and signals on it succeed. In 0.7.216.100-tester.27 Direct3D 12 read a wrong value, and a
  wait or a signal failed.
- **A Direct3D 12 texture that a Vulkan program opens now has its pixels in the right places (BD-118).** The 64-bit
  Vulkan driver uses the layout of the Direct3D 12 texture. It refuses a texture whose layout it cannot use, instead
  of reading its pixels at other positions.
- **HIP: a host buffer that starts where another one ends is now found (BD-123).** Copies and `hipMemset` on such a
  buffer now take the right route.

## Measured on our test board

These results come from the tests of the parts of this release on our own BC-250 on 2026-10-11, with the GPU
memory size at 8 GB and the automatic clock control on. The test of the complete package replaces them. Your
results can be different.

| Program | Mode | Result |
| --- | --- | --- |
| Quake II RTX, timedemo | ray tracing with `VK_KHR_ray_tracing_pipeline` | 66.92 frames per second |
| Quake II RTX, timedemo | ray tracing with `VK_KHR_ray_query` | 56.78 frames per second |
| vkd3d-proton tests, view instancing | Direct3D 12 | 2666 checks, 0 failures, 1 skipped |
| vkd3d-proton tests, render passes | Direct3D 12 | 1629 checks, 0 failures |
| vkd3d-proton tests, pipeline libraries | Direct3D 12 | 58 checks, 0 failures |

The two Quake II RTX lines are one run of each way, about 24 seconds each. They show that both ways of ray tracing
work with the Vulkan driver of this release. They do not show a change of speed against 0.7.216.100-tester.27: one
way was faster and the other slower, by about the spread between two runs of the same driver.

## Experimental: Vulkan presentation through DXGI

- The 64-bit Vulkan driver can show its pictures through DXGI, the way of Direct3D 12 games, in place of the GDI
  copy. GDI stays the default. To try DXGI for one program, set the environment variable
  `AMDGPU_WDDM_VK_WSI=dxgi` for that program. On our board, vkcube showed the right picture this way.
- If the DXGI way fails before its first picture, the driver goes back to GDI for that window and writes the
  reason in its log.
- **On the DXGI way, a full-screen Vulkan program can now show its pictures without the desktop compositor
  (independent flip).** The driver makes the swap chain in the shape that Windows needs for an independent flip,
  with three back buffers. On our board, a Vulkan test program took 2404 of its 2412 pictures this way. While a
  window of another program covers it, Windows composes the pictures as before.

## Known issues

- **Windows gets less memory when the GPU gets more.** At 12 GB, Windows on a 16 GB board has about 3.8 GB. That is
  enough for the desktop and a language model. Many games do not start with so little memory. Choose 12 GB for a
  program that needs the GPU memory, and 8 GB for games and everything else.
- **A board that does not start after a change of the memory size needs a CMOS clear.** The driver checks the
  board's settings memory before and after it writes, but it cannot check the next start of the board. A CMOS clear
  sets the size back to 8 GB. It also sets the boot order back to its default, so set it again after the clear.
- **The fixes of the Vulkan driver are in its 64-bit build only.** The 32-bit Vulkan driver of this release is the
  32-bit GPU driver of Direct3D 11 and 12, as in 0.7.216.100-tester.27. A 32-bit Vulkan program cannot use a GPU
  lock that it gets from another program.
- The Direct3D 12 driver needs the Direct3D 12 and Direct3D 11 GPU drivers of this release. Do not replace them
  with the files of another release. The Direct3D 12 driver then refuses to start, and a Direct3D 12 program
  fails or uses the Microsoft software renderer.
- **Ollama is a little slower than our llama.cpp build on the same path**, because it adds a server and a chat
  template around the same computation. The first answer after a start is slow, because the model must first go
  into the board's memory.
- **A model larger than the board's share of memory runs on the processor cores.** It becomes very slow, but it
  does not fail. A 12-billion-parameter model at the usual quality is about 7 GB and fits at 8 GB.
- The 64-bit Vulkan driver and the Direct3D 12 engine of this release are new builds, so the shader caches they
  wrote for an earlier release are not read any more. The first start of a game takes longer than it did, once.
- The known issues of 0.7.216.100-tester.27 apply, except the two that this release fixes: the Board memory card
  can change the size, and a Vulkan program can use a GPU lock that it gets from another program.

## Settings affected

- The installation keeps the settings that you changed. A setting that you did not change gets the new default of
  this release.
- **The GPU memory size is not a Windows setting.** It is kept in the board's own settings memory, and no
  installation and no uninstallation of this package changes it. If you choose 12 GB and then go back to an
  earlier release, the board stays at 12 GB.
- `HangRecoveryWaves` under the driver's `Parameters` key turns the record before a GPU reset on (1) or off (0).
  The INF does not write it. When the value is not there, the driver uses 1.
- **The Windows settings page changes Windows settings only when you ask it to.** The installer changes them only
  with `-ApplySystemTuning`. The uninstaller asks whether to restore the saved machine-wide settings. Enter keeps
  them. `uninstall.cmd -RestoreSystemTuning` restores them without the question, and `-KeepSystemTuning` keeps
  them.
- An extra writes its own per-user settings for the account that started `install.cmd`: `BC250_OLLAMA_BACKEND`,
  `BC250_OLLAMA_PORT` and the logon task `BC250 Ollama`. The uninstaller removes them.
- `DpmMaxMHz`, `SubmitWatchdogMs`, `FanLoadBoost`, `EnableDpAudioContainerId`, `EnableRingVmFlush` and `TdrDelay`
  stay as 0.7.216.100-tester.27 set them.

## If something goes wrong

- If the board does not start after a change of the memory size, clear the CMOS of the board. Then set the boot
  order again, and send us the support report from the next start.
- If the Board memory card shows a size that is not the size of your board, do not change it. Send us the support
  report.
- If a Direct3D 12 program starts on the Microsoft software renderer, check that all the files of this release are
  installed. Then send us the support report.
- If a Direct3D 12 game draws wrongly where it did not before, send us the support report with the name of the
  game and the settings you used.
- If a Vulkan program fails with `AMDGPU_WDDM_VK_WSI=dxgi`, remove the variable, check that the program works with
  GDI, and send us the support report.
- If a program stops and the screen goes black for a moment, the driver has reset the GPU. Run
  `bc250kmd_cli waves saved` as an administrator and send us its output with the support report.
- If the ray tracing benchmark stops without a number, send us the line it shows and the support report.
- If our Ollama does not use the board, send us the first twenty lines of
  `%LOCALAPPDATA%\bc250-ollama\server.log`.
- If a change on the Windows settings page fails, press "Refresh" and look at the item again. "Restore" restores
  only the settings that the page saved.
- Send us the support report from amdgpu-wddm Control. It holds the driver log and the stored graphics settings.
