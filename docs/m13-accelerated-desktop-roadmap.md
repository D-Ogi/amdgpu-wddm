# M13: accelerated Windows desktop

Planning checkpoint: 2026-09-24. Parent: [main roadmap](00-goal-and-roadmap.md), [ADR0009](adr/0009-native-d3d-umd-is-a-goal.md). This document defines work and acceptance tests. Measurements and their evidence remain in [facts.md](facts.md), especially M138-M139 and M145-M149.

## Number and priority

Keep M13, the existing native Direct3D and accelerated desktop milestone. Use M13.1-M13.7 for its gates. M8 retains its Vulkan compute acceptance criteria and completed result; M8.1 would blur the distinction between compute and desktop graphics. Milestone numbers identify scope, not execution order. The owner requested this breakdown after M8, then prioritised M9 inference before further desktop bring-up. On2026-09-24 the owner prioritized M13.1 visible display after two successful M9 warm starts (M404-M405). M9 remains open; desktop bring-up is the current work focus. This neither closes M9-M12 nor requires their entire application/conformance scope before desktop work can start.

The implementation route remains an experiment: reuse an existing open Direct3D frontend, prove a GPU backend, and update ADR0009 with the result. A CPU-rendered desktop is a diagnostic baseline. It cannot close M13.

## Route status (2026-09-26)

The gates table below is unchanged. Its "current position" column was written on 2026-09-24 and is not maintained here: the lab baseline is in workspace `STATE.md`, measured results in [facts.md](facts.md). Since that checkpoint, E34 measured a native D3D shader drawn through Zink/RADV with exact pixels (M531), a shared WDDM allocation imported into RADV on a second device and written by the GPU (M532, M533), and a hardware D3D device creating three runtime allocations through the runtime callbacks with `hKMResource` zero, cause unknown (M534). None of these closes M13.2 or M13.3.

The M13.3 route under implementation is recorded in [ADR 0017](adr/0017-graphics-stack-direction-after-m12.md): a hosted ICD, one Vulkan device per D3D runtime device driven through the runtime callbacks, with the existing `d3d10umd`/Zink build as the bring-up control and native path, and DXVK as the engine for a system D3D11 DDI beyond M13. Its first measured steps are M539 (hosted GPU fills through the runtime callbacks), M540 (persistent hosted screens) and M541 (rendering into runtime-owned shared allocations); none closes M13.2 or M13.3. The two-device sharing of M532/M533 is a diagnostic control: no documented way was found for a second device to open a runtime-created back buffer (`ref/m13-notes/zink-behind-d3d10umd.md`, section 9). A route becomes M13's route only through the ADR 0009 amendment described in the [main roadmap](00-goal-and-roadmap.md).

## Critical path and scope

Immediate path: M13.1 -> M13.2 -> M13.3 -> M13.4 -> M13.5 -> M13.6 -> M13.7. A bounded backend feasibility probe may start while sharing tests are being prepared, but cannot bypass an acceptance gate. Reuse proven M7/M8 and presentation work, and rerun their relevant regressions after KMD changes.

M13 targets the single BC-250 lab unit and its selected monitor/mode. Native D3D12, broad game compatibility, hardware video, all monitors/modes and production signing retain their existing separate scope. OS replacement is an alternative project decision, not evidence that Windows WDDM has passed; use the connected diagnostic USB for missing Linux reference measurements when required.

No calendar estimate or percent complete is assigned. Report the current gate, passed controls, remaining failing test and next experiment. A gate closes only with an evidence-bearing commit and facts.md entry. An S_OK, one successful boot or a desktop rendered on the CPU cannot establish full GPU acceleration.
