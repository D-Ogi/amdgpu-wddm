## 12:15 - the wrong door

Run 006 asked one question: does advancing `pDmaBuffer` make dxgkrnl submit? The answer is no, and the way it
says no is worth more than a yes would have been.

The fix works, exactly as far as it claimed to. Where run 005 built all four fills at shadow offset 0x0, run 006
walks them: 0x0, 0x140, 0x640, 0xB40, each starting where the last ended. dxgkrnl agrees from its own side - the
`BuildPagingBuffer` call at 83.898 s reports `65216 bytes free` of a 65536-byte buffer, which is 65536 minus the
320 bytes of the fill before it. VidMm is packing operations into one buffer and counting ours. M111.

And still no `SubmitCommand`. Zero calls in 110 seconds against 1581 `BuildPagingBuffer` calls. So M108's
pointer was a real defect that was not the defect.

The answer had been in every one of these logs since run 003, eight lines from the top:

    41      0.078 wddm: CreateContext node 1 engine 0x1 flags 0x00000005

`DXGK_CREATECONTEXTFLAGS`, bit 0 `SystemContext`, bit 2 `VirtualAddressing`. VidMm creates node 1's paging
context with virtual addressing, and a context that addresses virtually is submitted through
`DxgkDdiSubmitCommandVirtual` - the DDI this driver wired to node 0 and nothing else, with a software completion
at the bottom for everything that did not match. The paging buffers were being submitted the whole time. We were
retiring their fences ourselves, five lines below the branch that was supposed to run them, and the counter that
should have shown it up was `0 hardware submitted` - a number that looks identical whether dxgkrnl sent nothing
or sent everything to a door we had nailed shut.

Three things in the run say the same thing without needing the hardware to confirm it. `D3DKMTMakeResident`
returned `STATUS_PENDING` with a paging fence for each probe, and every probe completed - so the fence was
retired by something, and with no submission and no `SubmitCommand` there is exactly one candidate left.
`SubmitCommandVirtual` runs ahead of the `Present` count by exactly one per probe: 70/70, 83/82, 104/102,
122/119 - four fills, three submissions, because two of them shared a buffer. And the driver logged none of it,
because the desktop's own presents spent that DDI's log budget in the first five seconds of the run.

0.7.29 opens the other door. `DXGKARG_SUBMITCOMMANDVIRTUAL` has no submission offsets at all - it names a GPU
address - so the shadow offset comes from subtracting the buffer's own base, which `BuildPagingBuffer` is told
and now records. Anything that does not land inside that buffer is completed in software and counted, never
guessed: the shadow is a live ring's source, and a wrong subtraction there is not a wrong picture, it is a
wrong DMA. The logging is per node now, so no future run has to work out what came in on node 1 by subtracting
presents from submissions.

Nie ten klucz, te same drzwi (wrong key, same door). Run 007 is the first run that can test whether any of this
actually reaches SDMA0.
