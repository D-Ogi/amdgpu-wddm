## E21: the Linux side of the flip (03:30-04:00)

Fourth Linux reference session, one boot, amdgpu loaded once. The flip write sequence L20 asked for came back
small and fixed - nine named registers, lock/per-HUBP writes/unlock/trigger, the same order in all 360
repetitions of a 6 s run (M87). The surface address is a plain system physical byte address, not a shifted
one (M85, L23 closed). The firmware lights HUBP0 alone; amdgpu splits the same panel across HUBP0 and HUBP3,
960 each, the ODM combine E13 already saw (M86). The interrupt this kernel actually waits on for a flip is
not either candidate L24 named - it is the OTG vupdate-no-lock vector, and the two we guessed at are read but
never armed (M88, now wishlist L28). `DCSURF_SURFACE_INUSE` stayed 0 through the whole run regardless of
which address was live, which nobody has an explanation for yet (M89, L29).

Two false starts on the way, both left in the experiment README so the next person does not repeat them:
`modetest -v` over ssh reads EOF on stdin after the first flip and quits (no tty), so the first two attempts
each produced one flip and a straight face; holding stdin open with a trailing `sleep` pipe fixed it. And the
session script's own SMU kprobe never arms - it enables the event before creating it - so `smu-msgs.txt` in
the evidence is empty; the kprobe that did work was armed by hand before the Vulkan run.

That Vulkan run (vkcube, RADV, 20 s, KMS) is the other half of the day: under load this kernel sends the SMU
exactly one message, ever - the metrics-table read our own sampler triggers - and never asks for a different
clock. Sclk sits at 1500 MHz whether the GPU is idle or busy (M90). So `bc250rd`'s 1000 MHz / 820 mV
underclock is not recovering anything Linux already does; it is our own choice, on our own, all the way down.
Nie ma nic za darmo - there is no free lunch, not even one the SMU boots into for you.

The stick's toolset (`modetest`, `drm_info`, RADV/Mesa 26.1.6, `vulkaninfo`, `vkcube`, `scp`, `xxd`) is now
baked into `bc250/apks/` and `build_usb.py`'s package list, so the next session gets it without a network
install. The owner gave standing consent, if a future session ever needs it, to put an X server and a window
manager on the stick as well - not used this time, worth remembering before anyone reaches for a workaround.

Unit A ran Linux with amdgpu loaded once and never unloaded (facts M42, M55 say why nobody touches that).
The return to Windows turned out to need no owner at all (the owner said so in two words and an exclamation
mark): on the stick `grub.cfg` copied back from `.orig`, `efi/boot/bootx64.efi` renamed to `.off`, `sync`,
plain `reboot` at 04:04; Windows answered at 04:05 over Wi-Fi, NVMe present, `bc250kmd` display-only, 70 C.
So much for "requires a cold start". Kto pyta, nie błądzi (who asks does not go astray) - and who assumes, does.
