## E21: the Linux side of the flip (03:30-04:00)

Fourth Linux reference session, one boot, amdgpu loaded once. The flip write sequence L20 asked for came back
small and fixed - nine named registers, lock/per-HUBP writes/unlock/trigger, the same order in all 360
repetitions of a 6 s run (M87). The surface address is a plain system physical byte address, not a shifted
one (M85, L23 closed). The firmware lights HUBP0 alone; amdgpu splits the same panel across HUBP0 and HUBP3,
960 each, the ODM combine E13 already saw (M86). The interrupt this kernel actually waits on for a flip is
not either candidate L24 named - it is the OTG vupdate-no-lock vector, and the two we guessed at are read but
never armed (M88, now wishlist L28). `DCSURF_SURFACE_INUSE` stayed 0 through the whole run regardless of
which address was live, which nobody has an explanation for yet (M89, L29).

Two false starts on the way, both left in the experiment README so the next person does not repeat them:
`modetest -v` over ssh reads EOF on stdin after the first flip and quits (no tty), so the first two attempts
each produced one flip and a straight face; holding stdin open with a trailing `sleep` pipe fixed it. And the
session script's own SMU kprobe never arms - it enables the event before creating it - so `smu-msgs.txt` in
the evidence is empty; the kprobe that did work was armed by hand before the Vulkan run.

That Vulkan run (vkcube, RADV, 20 s, KMS) is the other half of the day: under load this kernel sends the SMU
exactly one message, ever - the metrics-table read our own sampler triggers - and never asks for a different
clock. Sclk sits at 1500 MHz whether the GPU is idle or busy (M90). So `bc250rd`'s 1000 MHz / 820 mV
underclock is not recovering anything Linux already does; it is our own choice, on our own, all the way down.
Nie ma nic za darmo - there is no free lunch, not even one the SMU boots into for you.

The stick's toolset (`modetest`, `drm_info`, RADV/Mesa 26.1.6, `vulkaninfo`, `vkcube`, `scp`, `xxd`) is now
baked into `bc250/apks/` and `build_usb.py`'s package list, so the next session gets it without a network
install. The owner gave standing consent, if a future session ever needs it, to put an X server and a window
manager on the stick as well - not used this time, worth remembering before anyone reaches for a workaround.

Unit A ran Linux with amdgpu loaded once and never unloaded (facts M42, M55 say why nobody touches that).
The return to Windows turned out to need no owner at all (the owner said so in two words and an exclamation
mark): on the stick `grub.cfg` copied back from `.orig`, `efi/boot/bootx64.efi` renamed to `.off`, `sync`,

So much for "requires a cold start". Kto pyta, nie błądzi (who asks does not go astray) - and who assumes, does.

## 11:15 - E24 run 004: both questions answered, one of them by a bugcheck

The run asked two things and got two answers, the second one at the price of the machine.

The control first: `fence gfx x2` with the ring up, and `ih state` went from nothing at all - 0 interrupts,
0 vectors, rptr and wptr both 0 - to 202 interrupts, 203 vectors consumed, rptr = wptr = 0x1960. The vectors
it printed are `client 4 source 87`: the display's own VUPDATE_NO_LOCK (M88), not the CP fence's client 20
source 181 (M79). So the IH ring does deliver the vsync interrupt, and M98's and M103's "nothing reaches the
IH" was an artefact of device starts with nothing running to deliver through. That is M106, and it puts the
flip's missing interrupt back on the table as a solvable thing.

Then `kmtprobe` held 512 MB, VidMm went to commit an allocation, and the machine died. This time with a dump.
Bugcheck 0x50 at `nt!_chkstk+0x36`, on `dxgmms2!VidMmWorkerThreadProc`, down through `PageInOneAllocation`,
`CommitResource`, `TransferToSegment`, `FillAllocationUsingGpuVa`, `DdiBuildPagingBuffer`, our
`Bc250WddmBuildPagingBuffer`, `GfxPagingBuild`, and into `bc250_sdma_paging_fill`, where the prologue tried to
take 0x5C00 bytes off a stack that had 24,576 in total and 0x12D0 of them already spent. The function declared
a `struct amdgpu_device` - 0x5B00 bytes - as a local, and so did its copy twin. They had been that way since
0.7.23, green in the host tests every time, because a user-mode thread has a megabyte of stack and `/W4 /WX`
has nothing to say about the difference. M104 and M105.

Two things came out of it besides the fix. The first is that M102's gap is closed on the interesting side:
VidMm *does* drive the paging node once memory is tight, and it arrives as a FILL on the way into a segment -
the exact call an idle desktop never makes. The second is `tools/win/stackbudget.py`, which walks the built
driver's own unwind records and fails the build at 4 KB of fixed frame; the positive control is the binary
that crashed, where it names those two functions at 23,576 bytes, and 0.7.26's largest frame anywhere is 872.
For scale, Microsoft's own dxgkrnl tops out at 4,296 and dxgmms2 at 2,808 - and both of them are already on
the stack when they call us. Cudze bledy sa najlepszym nauczycielem, ale swoje zapamietuje sie dluzej (other
people's mistakes are the best teacher, but you remember your own longer).


## 11:45 - E24 run 005: the node is right, dxgkrnl is not asking, and the vsync was working all along

0.7.26 walked into the run that killed 0.7.25 and came out the other side. Four `VIRTUAL_FILL`s, 872,415,232
bytes: 64 MB at physical 0x271C62000 in 80 dwords, 256 MB there twice in 320, then 256 MB at 0x281C62000. No
transfers, no insufficient-buffer, not one refusal of the five unsupported kinds, no TDR, no bugcheck, clean
undo, 67 to 72 C. The 64 MB fill's destination is the address run 004's dump carried in r8 - the same
allocation, an hour apart, with 0x5B00 bytes of stack the only thing that had changed. `VidMmTranslate` resolves
a live VidMm GPU VA; `PagingRangeContiguous` walks 65,536 pages of one 256 MB operation and finds them
contiguous; the emitters lay one CONST_FILL per 4 MB. H1 holds, and so does H2's build half (M107).

And none of it ran. `DxgkDdiSubmitCommand` was not called once in two minutes - it is absent from the DDI tally
altogether - and node 1 ends at 0 hardware submitted. dxgkrnl asked for four paging buffers and submitted none
of them (M108). The packets sat in the shadow buffer; SDMA0 never saw a byte. That is a better problem than the
one we had this morning: it is no longer about our packets, it is about what makes VidMm submit a paging buffer
at all, and that lives in caps and in whether an application that never waits on its paging fence gets its
operation carried out or quietly dropped.

Then, reading the same log for the third time, the line that had been in runs 003 and 004 as well:

    vidpn flip open: 1 hardware flips, 0 refused, 1 hardware vsyncs armed 2784 acked 0 refused 0 deferred
    vsync not enabled by ControlInterrupt, 0 ticks, 286 reported to dxgkrnl

The hardware vsync route is finished and has been since 0.7.24. OTG0's VUPDATE_NO_LOCK reaches the IH ring,
the ISR acknowledges 2784 of them at DIRQL, the DPC finds no flip pending every single time, and it reports
`DXGK_INTERRUPT_CRTC_VSYNC` to dxgkrnl for every tick dxgkrnl had enabled - 286 of them, none from the software
timer, which never ticked. M109. Three runs went hunting for that answer while the summary printed it each
time. Pod latarnia najciemniej (it is darkest under the lamp post).

What remains for the screen is M100, and 0.7.27 has the fix: the present path now copies into the surface the
scanout actually flipped to, mapped once per flip target rather than once per present. Built, clean, installed
with the gates shut, and the next run is the narrow one that shows the owner a desktop instead of noise.
